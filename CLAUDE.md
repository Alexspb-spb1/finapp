# FINAPP — правила выполнения remediation-плана в Claude Code

## 1. Источник истины

1. Обязательный план работ находится в `REMEDIATION_PLAN.md`.
2. Фактический код, конфигурация, тесты и развернутые правила важнее любых утверждений из `PROJECT_STATUS.md`.
3. `PROJECT_STATUS.md` разрешено использовать только как контекст, но не как доказательство.
4. За один рабочий цикл выполняется ровно один явно указанный пользователем пункт `TASK_ID`.
5. Никогда не выбирай и не начинай следующий пункт самостоятельно.
6. Не объединяй несколько пунктов плана в один PR, даже если они кажутся связанными.
7. Не ставь `[x]` в `REMEDIATION_PLAN.md`, пока пользователь не передал явный результат независимого ревью:

```text
REVIEW_RESULT: PASS
TASK_ID: <TASK-ID>
```

## 2. Роль Claude Code

Ты — исполнитель конкретного пункта плана, а не автор нового roadmap.

Твои обязанности:

- независимо перепроверить текущее состояние кода;
- воспроизвести проблему или зафиксировать исходное состояние тестом/проверкой;
- внести минимальные изменения строго в рамках текущего пункта;
- выполнить все доступные обязательные проверки;
- честно зафиксировать непроверенные части и блокеры;
- подготовить реализацию для независимого ревью;
- остановиться после текущего пункта.

Запрещено считать задачу выполненной только потому, что код компилируется или выглядит логично.

## 3. Обязательный протокол начала задачи

После получения `TASK_ID`:

1. Открой целиком описание этого пункта в `REMEDIATION_PLAN.md`, его зависимости, критерии приемки и соответствующий `GATE`.
2. Проверь, что все предыдущие обязательные пункты приняты и отмечены `[x]`.
3. Выполни и зафиксируй:

```bash
git status --short
git branch --show-current
git rev-parse HEAD
node --version
npm --version
```

4. Проверь `package.json`, имеющиеся npm scripts, Firebase-конфигурацию и относящиеся к задаче файлы.
5. Не удаляй, не откатывай и не перезаписывай чужие незакоммиченные изменения.
6. Если рабочее дерево содержит несвязанные изменения, которые мешают безопасной работе, остановись со статусом `BLOCKED` и перечисли их. Не используй `git reset --hard`, `git clean -fd` или принудительное восстановление файлов.
7. Создай или используй только ветку, указанную в пункте плана. Если ветка не указана, используй:

```text
remediation/<TASK-ID>-<short-description>
```

8. До изменения production-кода создай тест, воспроизводимый сценарий или объективное baseline-доказательство. Для чисто документационной/операционной задачи приложи проверяемые артефакты вместо искусственного теста.
9. Кратко перечисли план изменения, затем сразу выполни его. Не переходи к другой задаче.

## 4. Ограничение области изменений

Разрешены только изменения, необходимые для критериев приемки текущего `TASK_ID`.

Нельзя без прямого требования текущего пункта:

- выполнять большой рефакторинг соседних модулей;
- обновлять все зависимости;
- менять дизайн или продуктовую логику;
- переименовывать несвязанные файлы;
- форматировать весь репозиторий;
- менять схему Firestore;
- ослаблять Firestore Rules;
- добавлять временный fail-open fallback;
- скрывать проблему только на уровне UI;
- отключать TypeScript, ESLint или тестовые правила;
- добавлять `any`, `@ts-ignore`, `@ts-nocheck`, необоснованный `eslint-disable`;
- удалять failing tests или заменять содержательные проверки пустыми моками;
- менять lockfile без реальной необходимости текущей задачи;
- исправлять найденные соседние проблемы «заодно».

Соседние проблемы запиши в раздел `Дополнительные находки`, но не исправляй в текущем PR.

## 5. Защита внешних окружений

По умолчанию разрешена только локальная работа с файлами, тестами и Firebase Emulator Suite.

Без отдельного разрешения пользователя запрещено:

- выполнять `firebase deploy`;
- публиковать Firestore Rules или indexes;
- разворачивать Cloud Functions;
- читать, изменять или удалять production/staging данные;
- изменять Firebase Auth пользователей;
- запускать migration/backfill против внешнего проекта;
- создавать или удалять Firebase/GCP проекты;
- менять GitHub Secrets;
- выполнять destructive cloud-команды.

Для staging пользователь должен явно передать:

```text
EXTERNAL_ACTION_APPROVED: <TASK-ID>
ENVIRONMENT: staging
```

Для production требуется:

```text
PRODUCTION_ACTION_APPROVED: <TASK-ID>
BACKUP_REFERENCE: <идентификатор проверенной резервной копии>
ROLLBACK_REFERENCE: <описание или ссылка на проверенный rollback>
```

Даже при наличии разрешения сначала покажи точные команды, target project ID, ожидаемый эффект и rollback. Проверь, что выбран правильный Firebase project. Не используй production как значение по умолчанию.

Если задача требует ручного действия в Firebase Console или доступа, которого нет, не имитируй выполнение. Подготовь точную инструкцию/команду и заверши со статусом `BLOCKED — требуется действие владельца`.

## 6. Требования к безопасности и данным

1. Любая авторизация должна быть fail-closed.
2. Отсутствующий membership, неизвестная роль, ошибка чтения или поврежденный документ не должны повышать права.
3. UI-проверка роли не считается защитой Firestore.
4. Security Rules должны иметь emulator-тесты до deployment.
5. Privileged операции должны проверяться сервером.
6. Не логируй токены, пароли, service-account JSON, банковские данные и содержимое production-документов.
7. Не коммить `.env*`, кроме безопасного `.env.example`.
8. Не добавляй реальные project secrets в `VITE_*`.
9. Не удаляй и не преобразовывай реальные данные без backup, dry-run, idempotency, сверки и rollback.
10. Любая миграция обязана поддерживать повторный запуск без дублей.

## 7. Требования к финансовой логике

При изменении операций, счетов, split, переводов, валют, бюджетов, календаря или отчетов обязательно проверяй инварианты:

- сумма split равна исходной операции;
- add/update/delete не создают необъяснимое изменение остатка;
- перевод не создает и не уничтожает деньги вне явно зафиксированной FX-разницы;
- повторное выполнение команды не создает дубль, если команда заявлена как идемпотентная;
- `NaN`, `Infinity`, неверная дата и недопустимая сумма отклоняются;
- ошибка или частичное выполнение не показываются пользователю как успешное сохранение;
- закрытый период нельзя изменить без предусмотренного правила;
- отчеты проверяются на фиксированных эталонных данных, а не только snapshot-тестом JSX.

## 8. Проверки перед завершением

Сначала запусти узкие тесты текущей задачи, затем общий набор.

Обязательно проверь наличие и выполни доступные команды:

```bash
npm ci
npm run lint
npm run typecheck
npm run test:run
npm run test:rules
npm run test:e2e
npm run build
git diff --check
git status --short
```

Правила:

1. Не используй `|| true`, `--force`, `--no-verify` и другие способы скрыть ошибку.
2. Если script отсутствует, укажи `NOT AVAILABLE` и точную причину. Не утверждай, что проверка пройдена.
3. Добавляй отсутствующий script только когда это прямо входит в текущий пункт.
4. Если обнаружен существовавший до задачи сбой, докажи его baseline-командой/commit и все равно не называй общий check зеленым.
5. Если обязательный критерий не проверен, итоговый статус не может быть `READY_FOR_REVIEW`; используй `BLOCKED` или `PARTIAL`.
6. Для Rules используй Emulator Suite.
7. Для migration-задач приложи dry-run, counts, checksums, повторный запуск и rollback test.
8. Для производительности приложи измерение до и после на одинаковой production-сборке/fixture.

## 9. Коммиты, push и merge

1. Разрешено создавать локальную task-ветку.
2. До независимого ревью не выполняй merge в `remediation/main`, `main` или любую release-ветку.
3. Не выполняй push, если пользователь прямо не попросил.
4. После реализации и успешных проверок разрешен локальный сфокусированный commit:

```text
<TASK-ID>: <краткое описание>
```

5. Не переписывай опубликованную историю и не делай force-push.
6. После `CHANGES REQUIRED` внеси отдельный исправляющий commit или amend только если пользователь явно это указал.
7. После `PASS` обнови статус задачи и отчет, но по-прежнему не начинай следующий пункт.

## 10. Обязательный отчет

Создай или обнови:

```text
docs/remediation/reports/<TASK-ID>.md
```

И выведи в ответе тот же отчет:

```markdown
# <TASK-ID> — <название>

## Итоговый статус
READY_FOR_REVIEW | PARTIAL | BLOCKED

## Branch / commit
- branch:
- base SHA:
- result SHA:

## Проверенное исходное состояние
- что перепроверено;
- как воспроизведена проблема или зафиксирован baseline;
- почему вывод подтверждается кодом/тестом.

## Что изменено
- ...

## Почему изменения входят в текущий пункт
- ...

## Затронутые файлы
- ...

## Критерии приемки
- [x] ...
- [ ] ... — причина

## Проверки
| Команда | Результат | Примечание |
|---|---|---|
| `...` | PASS / FAIL / NOT AVAILABLE | ... |

## Фактический вывод существенных тестов
```text
...
```

## Security review
- ...

## Данные и миграция
- нет / описание;
- dry-run;
- idempotency;
- checksums;
- rollback.

## Ручная проверка
- ...

## Rollback
- точные действия возврата;
- что произойдет с данными.

## Известные ограничения
- ...

## Дополнительные находки вне scope
- ...

## Diff summary
```text
<git diff --stat>
```

## Следующий разрешенный пункт
- только ID и название;
- НЕ начинать его.
```

Не заявляй `READY_FOR_REVIEW`, если не выполнены все критерии приемки, которые можно выполнить на текущем шаге.

## 11. После независимого ревью

### При `CHANGES REQUIRED`

1. Открой замечания ревьюера.
2. Исправь только блокирующие замечания текущего `TASK_ID`.
3. Не начинай следующий пункт.
4. Добавь regression test для каждого подтвержденного дефекта, когда это применимо.
5. Повтори проверки.
6. Обнови отчет и верни задачу в `READY_FOR_REVIEW`.

### При `PASS`

1. Убедись, что `TASK_ID` совпадает с ревьюируемой задачей.
2. Замени `[ ]` на `[x]` только у этого пункта в `REMEDIATION_PLAN.md`.
3. Добавь в отчет дату и формулировку `Independent review: PASS`.
4. Выполни финальные проверки измененных файлов.
5. Создай финальный commit при необходимости.
6. Покажи следующий разрешенный `TASK_ID`, но не анализируй и не реализуй его.
7. Остановись.

## 12. Главный принцип

Одна задача → минимальный diff → доказательство → проверки → независимый review → PASS → отметка `[x]` → остановка.
