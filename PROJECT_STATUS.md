# FinApp — статус проекта

_Обновлено: 2026-07-13_

Документ фиксирует текущее состояние репозитория: что реализовано, какие
проблемы найдены при анализе и куда двигаться дальше. Актуализируйте его
по мере работы — это рабочая карта проекта, а не разовый отчёт.

---

## 1. Что это за проект

Веб-приложение управленческого учёта финансов для малого бизнеса:
операции (доходы/расходы/переводы), мультивалютные счета, бюджеты,
P&L, ДДС (CashFlow), баланс, платёжный календарь, прогнозы, проекты,
контрагенты, импорт банковских выписок, роли пользователей.

**Стек:** React 19 + TypeScript + Vite 8 + Tailwind CSS 4 + Firebase
(Auth + Firestore) + Zustand-подобный кастомный стор + Recharts +
dnd-kit + xlsx.

**Хостинг:** статика на GitHub Pages, деплой через
`.github/workflows/deploy.yml` при пуше в `main` (`npm ci && npm run build`,
ключи Firebase — из GitHub Secrets).

**Тестов нет вообще** (ни unit, ни e2e) — весь контроль качества сейчас
держится на TypeScript + ESLint + ручной проверке.

## 2. Архитектура данных

- Данные компании (счета, категории, операции, бюджеты, правила,
  платёжный календарь и т.д.) живут в модуле `src/store/companyStore.ts`
  как единый объект `CompanyData`.
- **Двойное хранение:** мгновенно пишутся в `localStorage`, затем
  асинхронно синхронизируются в Firestore (`company_data/{companyId}`).
  При загрузке сначала берутся данные из `localStorage` (без ожидания
  сети), затем подтягивается версия из Firestore, если она новее
  (`_savedAt`).
- Авторизация и роли — `src/store/authStore.ts` поверх Firebase Auth +
  коллекция `users`. Роли: `viewer` (только чтение) / `accountant` /
  `admin`. Проверка прав — **только на клиенте** (`useAuth().canWrite`,
  `readOnly` и т.д.).
- **В репозитории нет файла `firestore.rules`** — правила безопасности
  Firestore не версионируются в коде. Значит, реальная защита данных
  зависит от настроек в консоли Firebase, которые не видны и не
  проверяемы отсюда. Это стоит явно перепроверить (см. раздел 5).
- Один документ Firestore на компанию — при росте числа операций
  документ будет расти неограниченно (лимит Firestore — 1 МиБ на
  документ). Явного разбиения по коллекциям пока нет.

## 3. Что уже реализовано (страницы)

`src/pages`: Dashboard, Transactions, Accounts, Budget, Balance,
CashFlow, PnL, Forecast, Calendar, Counterparties, Projects +
ProjectDetail, Reconciliation, Import, Users, Settings, Login, Register.

Ключевые фичи по коммитам:
- Мультивалютные счета, группы категорий, ролевой доступ (viewer/accountant/admin).
- Дашборд с настраиваемыми виджетами (drag&drop, localStorage-персист).
- Импорт банковских выписок (`bankStatementParser.ts`) + сверка/дедупликация.
- Правила автокатегоризации, повторяющиеся операции (recurring), сплит операций.
- Прогнозы и тренды, платёжный календарь с блокировкой периода.

### Уже исправленные критичные баги (по истории коммитов)

В репозитории проводился предметный аудит, в коде остались метки
`БАГ №1`–`№11` — так помечены места, где были устранены проблемы:
двойной сабмит операций, операции в будущих датах вместо календаря,
пересчёт остатка при редактировании, наличные в минус, блокировка
закрытого периода, кумулятивный остаток в ДДС, `undefined`-поля ломали
Firestore-запись, строгий парсинг сумм, верхний предел суммы операции,
каскадное удаление ссылок (контрагент/проект), гонка при регистрации.
Похоже, это заведомо тестовый/учебный проект с намеренно внесёнными и
затем исправленными багами — учитывайте это при дальнейшем аудите.

## 4. Технические проблемы, найденные сейчас

### 4.1 Сборка — OK
`npm run build` (`tsc -b && vite build`) проходит чисто, без ошибок
типов. Стартовое состояние `node_modules` было повреждено (не было
`@eslint/js`, тайпингов vite/node) — это чинится `npm ci`, теперь
починено.

### 4.2 ESLint — 42 ошибки, 3 предупреждения

`npm run lint` не проходит. Категории:

| Категория | Где | Суть |
|---|---|---|
| **Компонент создаётся внутри render** (`react-hooks/static-components`) | `PnL.tsx` (SectionRows, SummaryRow — 4 использования), `Budget.tsx` (CatSection — 2), `ProjectDetail.tsx` (CustomTooltip — 2) | Вложенные функции-компоненты объявлены внутри тела родительского компонента → пересоздаются и теряют состояние на каждый ре-рендер. Нужно вынести их наружу (передавая нужные данные пропсами). |
| **setState синхронно в useEffect** (`react-hooks/set-state-in-effect`) | `Layout.tsx`, `Accounts.tsx`, `SplitTransactionModal.tsx`, `TransactionEditModal.tsx`, `TransactionModal.tsx` (x3) | Может провоцировать лишние каскадные ре-рендеры. Не крашит, но следует пересмотреть по возможности. |
| **Impure-вызов в render** (`react-hooks/purity`) | `TransactionModal.tsx:130` — `Date.now()` при формировании id операции | Id должен генерироваться в обработчике сабмита, а не быть частью «чистого» рендера. |
| **Переменная используется до объявления** | `Transactions.tsx:183` — `filtered` читается в `useEffect` выше своего `const filtered = ...` | Работает благодаря hoisting/порядку эффектов, но хрупко — при рефакторинге легко словить баг. Стоит переставить объявление `filtered` выше эффекта. |
| **`any`** (`@typescript-eslint/no-explicit-any`) | `authStore.ts`, `companyStore.ts` (x2), `Dashboard.tsx` (x2), `CashFlow.tsx` (x2), `Forecast.tsx` (x2), `ProjectDetail.tsx` (x2), `MatchmakerModal.tsx`, `TransactionRulesModal.tsx` | Слабая типизация в проблемных местах — стоит завести нормальные типы. |
| **Пустые блоки** (`no-empty`) | `companyStore.ts` (x2), `Dashboard.tsx` | `catch {}` без обработки — осознанно (best-effort localStorage), но lint ругается; либо добавить комментарий-игнор, либо явный no-op. |
| **`a ? b() : c()` как statement** (`no-unused-expressions`) | `StatementPreview.tsx`, `Counterparties.tsx`, `Dashboard.tsx`, `Transactions.tsx` | Тернарник вместо `if`; работает, но не по стайлгайду ESLint. |
| **Незакрытая зависимость useEffect/useCallback** (warning) | `Forecast.tsx`, `Import.tsx`, `SplitTransactionModal.tsx` | Возможны стейл-замыкания при определённых сценариях. |

Ни одна из ошибок не ломает сборку и рантайм не падает, но линт в CI не
подключён — эти проблемы будут только копиться.

### 4.3 npm audit — 3 уязвимости

- `@babel/core` — low, есть автофикс.
- `vite 8.0.0–8.0.15` — **high** (NTLMv2 hash disclosure на Windows,
  обход `server.fs.deny`), есть автофикс через `npm audit fix`.
- **`xlsx`** — **high**, Prototype Pollution + ReDoS, **фикса от
  разработчика нет**. Библиотека используется для импорта/экспорта
  банковских выписок и Excel-отчётов (`src/utils/exportExcel.ts`,
  `bankStatementParser.ts`) — то есть обрабатывает файлы, загружаемые
  пользователем. Это прямой риск.

### 4.4 Прочее

- Итоговый бандл — **один JS-чанк 1.88 МБ (540 КБ gzip)**, Vite явно
  предупреждает о превышении 500 КБ. Нет `dynamic import()` / роутового
  код-сплиттинга — все страницы (включая тяжёлые Recharts/xlsx/dnd-kit)
  грузятся одним куском.
- CI (`deploy.yml`) выполняет только `npm run build` — не гоняет
  `npm run lint`, тесты (которых нет) отсутствуют вовсе. Ничто не
  мешает смёрджить код с ошибками линта или регрессией.
- `firestore.rules` не хранится в репозитории — не подлежит ревью и
  версионированию вместе с кодом.
- `.env.local` в среде анализа отсутствует (ожидаемо — ключи не должны
  быть в репо), из-за чего локально Firebase Auth падает с
  `auth/invalid-api-key`. Это нормально для чистого клона, но
  напоминание: чтобы кто-то новый мог поднять проект локально, нужны
  реальные значения `.env.example` → `.env.local`.

## 5. Куда двигаться — приоритеты

### Высокий приоритет
1. **Убрать/заменить `xlsx`** или изолировать его так, чтобы парсинг
   вёлся не над произвольным присланным файлом без ограничений
   (санитайзинг, лимит размера, возможно воркер с таймаутом) — high-severity
   уязвимости без фикса.
2. **Вынести `firestore.rules` в репозиторий** и прогнать ревью: сейчас
   контроль доступа (viewer/accountant/admin) реализован только на
   клиенте — без серверных правил Firestore это не защита, а
   UI-подсказка. Любой авторизованный пользователь потенциально может
   обратиться к Firestore напрямую в обход клиентских проверок.
3. **Подключить `npm run lint` (и `tsc --noEmit`) в CI** — сейчас деплой
   проходит, даже если линт красный.

### Средний приоритет
4. Вынести компоненты, создаваемые внутри render (`PnL.tsx`,
   `Budget.tsx`, `ProjectDetail.tsx`) — иначе они на каждый ре-рендер
   теряют внутреннее состояние (для `CustomTooltip`/`SectionRows` пока
   не критично, но это тикающая мина при дальнейшем усложнении).
5. Код-сплиттинг по роутам (`React.lazy` + `Suspense`) — уменьшит
   первый TTI, особенно на мобильных сетях.
6. Обновить `vite` и `@babel/core` (`npm audit fix`) — фиксы есть, риска
   минимум.
7. Разобраться с `Date.now()` в рендере `TransactionModal.tsx` и с
   порядком объявления `filtered` в `Transactions.tsx`.

### Низкий приоритет / гигиена
8. Убрать `any` в перечисленных файлах, поставить нормальные типы.
9. Добавить хотя бы базовый набор unit-тестов на денежную логику
   (`currency.ts`, `companyStore.ts` — расчёт остатков, блокировка
   периода, каскадные удаления) — это самое рискованное место в
   финансовом приложении, а тестов там нет вообще.
10. Разбить единый Firestore-документ на компанию, если объём данных
    (число операций) начнёт расти — риск упереться в лимит 1 МиБ/документ.

## 6. Как проверять локально

```bash
npm ci               # чистая установка (важно — не npm install при битых node_modules)
npm run lint          # ESLint (сейчас красный, 42 ошибки)
npm run build          # tsc -b && vite build — должен быть зелёным
npm run dev             # dev-сервер, http://localhost:5173/finapp/
npm audit                # проверка уязвимостей зависимостей
```

Для локального входа нужен `.env.local` (см. `.env.example`) с реальными
ключами Firebase-проекта — без них `auth/invalid-api-key` при попытке
логина.
