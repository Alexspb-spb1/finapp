# ADR-001 — Каноническая модель членства компаний и ролей

## Title

Каноническая модель членства (company membership) и ролей для FinApp.

## Status

**Accepted as target architecture.**

Этот ADR фиксирует целевую модель. **Реализация ещё не выполнена.** Ни код
приложения (`src/**`), ни Firestore Rules, ни тесты, ни зависимости не
менялись в рамках `SEC-001` — этот документ ничего не деплоит и не включает.
Реализация распределена по последующим задачам `SEC-002`–`SEC-006` (см.
раздел «Rollout dependencies»). До завершения этих задач в production
продолжают действовать существующие **emergency Rules** (`BASE-004A`) — они
остаются в силе и не заменяются этим ADR автоматически.

## Date

2026-08-02

## Context

FinApp — SPA без собственного backend (нет Cloud Functions, нет custom
claims). До `BASE-004A` фактически развёрнутые production Firestore Rules
разрешали любому авторизованному пользователю свободно менять поля
`role`/`companyId`/`companies[]` в собственном документе `users/{uid}` —
это давало полную межарендную (cross-tenant) эскалацию привилегий,
классифицированную как **CRITICAL/SECURITY_RISK_C**
(`docs/remediation/SECURITY_BASELINE.md`).

`BASE-004A` — экстренный (emergency) патч, не финальная архитектура. Он
запрещает клиенту менять авторизационные поля `users/{uid}` вообще (allowlist
`name`/`avatar` на self-update, полный запрет `update`/`delete` чужого
документа), что закрывает CRITICAL/HIGH уязвимости, но как прямое следствие
ломает клиентские сценарии управления пользователями (регистрация новой
компании, приглашение сотрудника, смена роли, удаление сотрудника,
добавление доп. компании) — они требуют серверного пути, которого пока нет.
Это зафиксированный, осознанно принятый архитектурный долг, а не
предположение о будущем.

### Текущее фактическое состояние (legacy) и пробелы безопасности

Изучены: `firestore.rules`, `src/types/auth.ts`, `src/store/authStore.ts`,
`src/store/companyStore.ts`, `src/pages/Users.tsx`, `src/hooks/useAuth.ts`,
`docs/remediation/SECURITY_BASELINE.md`,
`docs/remediation/BASE-004A_EMERGENCY_RULES_PLAN.md`. Честно фиксируется:

1. Права в приложении берутся из документа `users/{uid}`: полей `role`
   (домашняя/основная роль), `companyId` (домашняя компания) и `companies[]`
   (массив `{companyId, role}` для дополнительных компаний). Отдельной
   server-controlled подколлекции членства не существует.
2. `activeCompanyId` — выбор активной компании — хранится **на клиенте**, в
   `localStorage` (`authStore.ts`, ключ `finapp_active_company`), а не в
   какой-либо доверенной серверной структуре.
3. `authStore.getEffectiveRole()` (`src/store/authStore.ts:431-437`)
   содержит явный **fallback на домашнюю роль**: если для активной
   дополнительной компании не находится membership в `currentUser.companies`,
   функция возвращает `currentUser.role` (роль домашней компании) вместо
   отказа в доступе — `return membership?.role ?? currentUser.role`.
4. При отсутствии документа `users/{uid}` (`authStore.ts:84-129`,
   `onAuthStateChanged`) существует **клиентское авто-восстановление**:
   создаётся новый профиль с `role: 'admin'` и новая компания, без какой-либо
   серверной проверки, что это легитимный владелец. Успех записи в Firestore
   не гарантирован (перехватывается ошибка), но восстановленные данные всё
   равно используются в памяти немедленно.
5. Управление пользователями и компаниями частично выполняется клиентом:
   `inviteUser()` создаёт Firebase Auth-аккаунт через REST API и пишет
   `users/{newUid}` напрямую с клиента; `updateUser()` меняет чужую роль
   через `updateDoc`; `removeUser()` удаляет чужой документ через
   `deleteDoc`; `createCompany()` дописывает `companies[]` в свой же
   документ. Все эти клиентские вызовы фактически **уже отклоняются**
   текущими emergency Rules (`allow update: if false` для чужого документа,
   `delete` запрещён для всех, self-update ограничен allowlist `name`/
   `avatar`) — но сам клиентский код всё ещё пытается это делать, то есть
   архитектурно эти операции остаются client-initiated write, просто
   сегодня блокируются на уровне Rules, а не отсутствуют в коде.
6. Emergency Rules (`BASE-004A`) запрещают клиентское изменение
   авторизационных полей `users/{uid}` — это **временное ограничение**,
   явно описанное как emergency-подход (п.3 из трёх вариантов, перечисленных
   в `BASE-004A_EMERGENCY_RULES_PLAN.md`, раздел 2), а не постоянное решение
   в духе целевой архитектуры (серверная `members` подколлекция +
   callable Cloud Functions).
7. **Текущий код не соответствует целевой модели `SEC-001`.** Нет
   коллекции `companies/{companyId}/members/{uid}`, нет статуса
   `invited`/`active`/`disabled`, нет проверки last-admin, `ownerId`
   трактуется в некоторых местах (`companyStore.ts` fallback на
   `auth.currentUser?.uid` как `saveId`) неформально, а не как чётко
   определённая юридическая связь.
8. **Этот PR (`SEC-001`) не устраняет ни одно из перечисленных
   расхождений и не утверждает, что новая модель уже работает.** Он
   только фиксирует целевую архитектуру для последующих задач.

## Decision

Принять единственную каноническую модель членства и ролей, описанную ниже,
как целевую архитектуру для всех последующих задач раздела `SEC-*`.
Источником истины для авторизации становится исключительно
server-controlled подколлекция `companies/{companyId}/members/{uid}`.
`users/{uid}` остаётся глобальным профилем без каких-либо авторизационных
полномочий.

## Canonical data model

```text
companies/{companyId}
companies/{companyId}/members/{uid}
users/{uid}
```

### `users/{uid}` — только глобальный профиль

Содержит исключительно данные профиля (имя, email, аватар, настройки
интерфейса). **Ни одно поле этого документа не является источником прав.**
Ни Rules, ни серверные функции не должны читать `users/{uid}` для принятия
решения о доступе к данным какой-либо компании. Легаси-поля `role`,
`companyId`, `companies[]` в этой коллекции **не удаляются немедленно**
(см. «Legacy migration implications»), но перестают на что-либо влиять
после переключения источника прав на `members`.

### `companies/{companyId}` — метаданные компании

Название, реквизиты, валюта, `ownerId` (см. «ownerId semantics» ниже).
Не хранит списка участников и ролей.

### `companies/{companyId}/members/{uid}` — источник прав

```ts
{
  uid: string
  role: 'viewer' | 'accountant' | 'admin'
  status: 'invited' | 'active' | 'disabled'
  createdAt: Timestamp
  updatedAt: Timestamp
  invitedBy?: string
}
```

## Source of authorization truth

`companies/{companyId}/members/{uid}` — единственный источник авторизации
для операций в рамках компании `companyId`. Ничего другое (ни
`users/{uid}`, ни `localStorage`, ни клиентский state, ни `ownerId`) не
может служить доказательством прав.

### Обязательные инварианты

1. ID membership-документа равен Firebase Auth UID вызывающего.
2. Поле `uid` внутри документа должно совпадать с ID документа (двойная
   проверка против подмены).
3. Авторизацию даёт только `status == 'active'`.
4. `status == 'invited'`, `status == 'disabled'`, отсутствующий или
   повреждённый (не прошедший схему) membership-документ **всегда** дают
   отказ в доступе к данным компании — никаких исключений.
5. Неизвестное значение `role` (не входящее в перечисление
   `viewer`/`accountant`/`admin`) всегда приводит к отказу.
6. Отсутствие документа membership для пары `(uid, companyId)` всегда
   приводит к отказу.
7. `createdAt` и `updatedAt` управляются исключительно доверенным сервером
   (Cloud Function / Admin SDK) — клиент не может их установить или
   изменить напрямую.
8. Клиент не может напрямую создавать, изменять или удалять документы
   `members/*` через Firestore SDK. Единственный путь — доверенная
   серверная операция.
9. Email, отображаемое имя, `ownerId`, значения из `localStorage` или
   `companyId`, переданный клиентом в запросе, никогда не могут служить
   доказательством членства — доказательством является только факт
   существования и содержимое конкретного документа
   `companies/{companyId}/members/{uid}`.
10. Роль никогда не переносится из одной компании в другую — `role` в
    `members/{uid}` одной компании не имеет никакого отношения к правам
    того же `uid` в другой компании.

### Pre-acceptance invitation — точное решение

- До того момента, как приглашение принято, источником состояния
  приглашения является отдельная будущая сущность `invitations`
  (детальная схема — предмет `SEC-006`, не определяется в этом ADR).
- **Нельзя** использовать email или произвольно выдуманный UID как ключ
  документа `members/{uid}` — ключ обязан быть реальным Firebase Auth UID.
- Документ `members/{uid}` создаётся или активируется сервером **после**
  подтверждённого принятия приглашения — то есть только тогда, когда
  реальный Firebase Auth UID приглашённого уже известен (пользователь
  зарегистрировался/вошёл и подтвердил приглашение).
- `status: 'invited'` membership-документ **допустим создавать заранее**,
  но только если реальный UID уже известен (например, приглашённый уже
  имеет Firebase Auth аккаунт под известным email/uid) — и такой документ
  **всё равно не даёт доступа** ни к чтению, ни к записи данных компании,
  пока `status` не станет `'active'`.

## Role and permission matrix

Обозначения: **allow** — разрешено немедленно (subject to `status ==
'active'` для всех non-owner операций компании); **deny** — запрещено
безусловно; **server-only** — операция обязана выполняться доверенной
серверной функцией (Cloud Function / Admin SDK), а не напрямую клиентским
Firestore SDK, даже если инициируется admin'ом.

| Ресурс / операция | viewer | accountant | admin | Примечание |
|---|---|---|---|---|
| **Company metadata** — чтение | allow | allow | allow | видимость метаданных доступна всем активным участникам |
| **Company metadata** — изменение (name/legalType/inn/currency) | deny | deny | allow | admin этой конкретной компании |
| **Financial data (company_data)** — чтение | allow | allow | allow | только своей компании |
| **Accounts** — чтение | allow | allow | allow | |
| **Accounts** — создание/изменение/удаление | deny | allow | allow | |
| **Categories / reference data** — чтение | allow | allow | allow | |
| **Categories / reference data** — изменение | deny | allow | allow | |
| **Transactions** — чтение | allow | allow | allow | |
| **Transactions** — создание/изменение/удаление | deny | allow | allow | закрытый период — см. отдельный инвариант ниже |
| **Projects / budgets** — чтение | allow | allow | allow | |
| **Projects / budgets** — изменение | deny | allow | allow | |
| **Closing period (closingDate)** — чтение | allow | allow | allow | |
| **Closing period (closingDate)** — изменение | deny | deny | allow | только admin — сохраняет существующую бизнес-логику (`BASE-004A`) |
| **Member directory** — чтение списка участников своей компании | allow | allow | allow | только участники своей компании; чужая компания — deny |
| **Membership / role management** (создание/смена role/status) | deny | deny | server-only | даже admin не пишет `members/*` напрямую из браузера — см. ниже |
| **Company security settings** (будущие security-специфичные настройки) | deny | deny | server-only | привилегированная операция, требует серверной проверки last-admin/аудита |
| **Invitations** — создание/отзыв | deny | deny | server-only | admin инициирует, но фактическая запись — сервер |
| **Invitations** — принятие (сам приглашённый) | server-only | server-only | server-only | принятие — доверенная серверная операция, активирующая membership |
| **Audit events** — чтение | deny | deny | allow | admin компании; audit — привилегированная видимость |
| **Audit events** — запись | server-only | server-only | server-only | пишется исключительно сервером/Rules-доверенным путём, не произвольным клиентским `setDoc` |
| **Company deletion** | deny | deny | server-only | необратимая операция — только доверенная серверная процедура с явными предохранителями (см. «ownerId semantics») |

### Дополнительные явные решения

- `accountant` не управляет компанией, ролями, участниками, приглашениями
  или security-настройками ни при каких условиях — таблица выше не оставляет
  для этого «серых» ячеек.
- `admin` — управление компанией и участниками **строго в пределах
  конкретной компании**, которой он администратор. Роль `admin` **не
  является глобальным администратором** системы.
- Даже `admin` **не пишет `members/*` напрямую из браузера**: любое
  изменение роли, статуса, приглашение, отзыв доступа проходит через
  callable Cloud Function, которая проверяет вызывающего как `admin`
  соответствующей компании, атомарно проверяет last-admin инвариант (см.
  ниже) и только затем пишет `members/*` от имени Admin SDK. Firestore
  Rules для `members/*` должны запрещать прямую клиентскую запись
  безусловно (`allow write: if false` для клиентских SDK-запросов — это
  требование к будущей реализации Rules в `SEC-003`/`SEC-011`, не
  выполняется в этом ADR).
- Глобальные операции Firebase Auth (отключение аккаунта, смена email,
  удаление Auth-пользователя целиком) **не следуют автоматически** из роли
  admin одной компании — это отдельная административная плоскость (см.
  «Auth-account lifecycle»).

## Membership lifecycle

1. **Создание.** Приглашение сотрудника или first-admin-регистрация новой
   компании инициирует создание `members/{uid}` **сервером**, после того как
   реальный UID известен.
2. **`invited` → `active`.** Переход выполняется сервером после
   подтверждённого действия приглашённого пользователя (принятие
   приглашения). Пока статус `invited`, доступа к данным компании нет.
3. **`active` → `disabled`.** Инициируется admin'ом компании через
   серверную функцию; немедленно лишает доступа ко всем ресурсам компании.
   Не удаляет исторические данные (кто создал транзакцию и т.д. — те записи
   не переписываются).
4. **`disabled` → `active`.** Повторная активация — та же серверная функция,
   те же проверки прав, что и при создании.
5. **Удаление документа membership** — не основной путь лишения доступа
   (предпочтителен `disabled`), но допустим сервером для полной очистки
   (например, при удалении компании целиком). Прямое клиентское удаление
   запрещено безусловно.

## Multi-company behavior

- Один пользователь (один Firebase Auth UID) может иметь **независимые**
  membership-документы в нескольких компаниях одновременно —
  `companies/{A}/members/{uid}` и `companies/{B}/members/{uid}` — это два
  отдельных, никак не связанных документа.
- Роль определяется **отдельно для каждой компании**. Роль `admin` в
  компании A не подразумевает никакой роли (даже `viewer`) в компании B.
- Выбранная в UI «активная компания» (аналог сегодняшнего
  `activeCompanyId`) — это **исключительно контекст отображения**, а не
  источник полномочий. Она может продолжать храниться на клиенте
  (например, в `localStorage`) для UX-удобства, но не участвует ни в одном
  решении о доступе.
- Сервер и Firestore Rules **заново проверяют membership для каждого
  `companyId`** на каждой операции — не полагаются на то, какая компания
  была «активной» на клиенте в момент запроса.
- Домашней/главной роли, автоматически распространяющейся на другие
  компании, не существует — в отличие от сегодняшнего `getEffectiveRole()`
  fallback на `currentUser.role`, целевая модель делает это невозможным по
  построению: каждая проверка обязана явно указывать `companyId` и читать
  ровно один документ `members/{companyId}/{uid}`.
- Удаление или `disabled` статус membership в одной компании **не влияет**
  на memberships пользователя в других компаниях — каждый документ
  независим.
- Удаление пользователя из **последней** компании, где он состоял, **само
  по себе не удаляет** Firebase Auth account — это отдельная, явно
  инициируемая операция (см. «Auth-account lifecycle»).
- Получить список или данные чужой компании через подбор/угадывание
  `companyId` невозможно: каждая операция чтения/записи данных компании
  обязана пройти проверку `members/{companyId}/{uid}.status == 'active'`
  для точного запрошенного `companyId` — угаданный, но чужой `companyId`
  всегда даёт `deny`, независимо от того, состоит ли пользователь в каких-то
  других компаниях.

## Privileged operations

Все операции, перечисленные как `server-only` в матрице ролей выше
(membership/role management, security settings, invitations,
company deletion, audit-запись), выполняются исключительно доверенными
серверными функциями (Cloud Functions с Admin SDK — реализация в
`SEC-003`). Клиент инициирует запрос (например, кнопка «Пригласить
сотрудника»), но фактическая проверка прав, атомарность и запись в
Firestore происходят на сервере, а не через прямой Firestore SDK вызов
из браузера.

## Last-admin invariant

- В каждой действующей (не удалённой) компании должен существовать
  **минимум один** membership со `status == 'active'` и `role == 'admin'`.
- Нельзя удалить, отключить (`disabled`) или понизить в роли **последнего**
  активного admin компании — ни через UI, ни через прямой вызов серверной
  функции с валидным admin-токеном другого пользователя.
- Проверка этого инварианта выполняется **исключительно доверенной
  серверной операцией в транзакции** (Firestore transaction/Cloud Function
  с блокировкой на чтение количества активных admin перед разрешением
  изменения) — не в Firestore Rules (Rules не могут атомарно посчитать
  «остался ли ещё один admin» при конкурентных запросах без риска race
  condition) и не клиентской логикой.
- Клиентская проверка (например, скрытая/задизейбленная кнопка «Удалить»
  в UI) **недостаточна** — она не является защитой и легко обходится
  прямым запросом к серверной функции; серверная сторона обязана повторно
  проверить инвариант независимо от того, что показал клиент.
- Конкурентные запросы (два одновременных запроса на удаление/понижение
  двух разных admin одной и той же компании) не должны допускать race
  condition, при которой оба запроса проходят проверку «остался ли ещё один
  admin» до того, как любой из них применит изменение, и в результате
  компания остаётся без единого активного admin. Транзакционная проверка
  обязана быть атомарной относительно этого сценария.

## `ownerId` semantics

- `ownerId` в `companies/{companyId}` — это **справочная/юридическая
  связь** (кто изначально создал компанию / кто юридически ответственен),
  а не механизм авторизации.
- `ownerId` **не даёт доступ** к данным компании и **не обходит**
  проверку membership. Пользователь с `ownerId == uid`, но без активного
  membership в `companies/{companyId}/members/{uid}`, не имеет доступа к
  `company_data`, не может читать/писать финансовые данные, не является
  admin автоматически.
- Чтобы фактически работать с компанией (включая административные
  действия), владелец обязан иметь отдельный, полноценный `active admin`
  membership-документ — точно такой же, как у любого другого admin.
- Изменение `ownerId` (передача владения) и восстановление компании после
  ситуации без единого admin (например, после ошибки миграции) требуют
  **отдельной, явно определённой серверной процедуры** — не покрываются
  этим ADR детально и не реализуются как побочный эффект обычных
  membership-операций. Эта процедура — предмет отдельной будущей задачи,
  не `SEC-001`–`SEC-006`.

## Auth-account lifecycle

- Firebase Auth account (сам факт существования логина/пароля/email,
  возможность аутентифицироваться) — это **отдельная плоскость** от
  company membership.
- Лишение доступа ко всем компаниям (через `disabled`/удаление всех
  memberships) **не обязано** и по умолчанию **не должно** автоматически
  отключать или удалять Firebase Auth аккаунт целиком — пользователь может
  оставаться зарегистрированным в системе без активного членства ни в одной
  компании (например, ожидая нового приглашения).
- Полное отключение/удаление Firebase Auth аккаунта — отдельная
  привилегированная global-операция, не следующая автоматически из роли
  `admin` какой-либо одной компании (см. также «Role and permission
  matrix» — `admin` не является глобальным администратором).

## Legacy migration implications

- Легаси-поля `role`, `companyId`, `companies[]` в `users/{uid}` **нельзя
  удалять** до выполнения backfill (`SEC-005`) и проверенного переключения
  чтения прав на `members` (`SEC-003`/`SEC-011`).
- До полного переключения приложение физически продолжает частично
  полагаться на текущие поля `users/{uid}` (см. «Current state» выше) —
  это ожидаемое переходное состояние, а не нарушение этого ADR: сам ADR не
  требует немедленной миграции, только фиксирует целевую точку.
- Backfill обязан быть идемпотентным, проверяемым (dry-run, checksums,
  повторный запуск без дублей) — детали реализации, не фиксируемые в этом
  документе, относятся к `SEC-005`.

## Security invariants

Явно запрещены следующие практики (fail-closed по умолчанию):

- Fallback на `users/{uid}.role` как источник прав.
- Fallback на «домашнюю» (primary/home) роль пользователя при отсутствии
  membership для запрошенной компании.
- Fallback на `ownerId` как доказательство прав.
- Любой fallback при отсутствующем membership-документе — отсутствие
  документа означает `deny`, никогда не `allow` с ролью по умолчанию.
- Любой fallback при ошибке чтения Firestore (permission-denied, network
  error, timeout) — ошибка чтения означает `deny`, а не «попробовать
  восстановить»/«считать, что всё ок».
- Роль, полученная из `localStorage` или любого другого клиентского
  хранилища.
- Роль, полученная из UI-состояния (то, что показал предыдущий экран).
- Роль или `uid`, переданные в теле запроса клиентом, без независимой
  серверной сверки по токену аутентификации (`request.auth.uid` в Rules /
  проверенному ID-токену в Cloud Function) — клиентски заявленный
  `uid`/`role` в payload никогда не считается достоверным сам по себе.
- Автоматическое повышение повреждённой или неизвестной роли до `admin`
  (или любой другой роли) — повреждённые/неизвестные значения всегда
  `deny`, никогда не «безопасный default».

Ошибки чтения, повреждённые документы и неизвестные значения полей
завершаются отказом доступа — не восстановлением привилегий, не тихим
fallback-значением, не попыткой «угадать» намерение.

## Rejected alternatives

| Альтернатива | Причина отказа |
|---|---|
| Роли внутри `users/{uid}` (текущая legacy-модель) | Смешивает глобальный профиль пользователя с авторизацией конкретной компании; один документ, изменяемый пользователем (даже частично), структурно не может быть надёжным источником прав для multi-tenant модели — именно эта архитектура привела к CRITICAL-уязвимости `BASE-004`. |
| Массив `companies[]` как источник прав | Тот же документ `users/{uid}`, та же проблема доверия клиентски-читаемому/потенциально изменяемому массиву; кроме того, массивы плохо поддерживают атомарные точечные Rules-проверки без риска race condition при параллельных membership-изменениях и не дают естественного места для server-managed `createdAt`/`updatedAt` на уровне отдельного membership. |
| Firebase custom claims как единственный источник часто меняющихся company memberships | Custom claims требуют принудительного обновления ID-токена клиентом (`getIdToken(true)`) после каждого изменения роли — при частых изменениях (приглашения, смена ролей, disable) это даёт задержку/несогласованность между «фактическим» состоянием на сервере и тем, что видит клиент; claims также ограничены по размеру (1000 байт суммарно), что плохо масштабируется на пользователя с memberships во многих компаниях. |
| `ownerId` как авторизационный bypass | Смешивает юридическую/справочную связь с фактическим правом доступа; позволяет владельцу компании, покинувшему активное членство (например, после сознательного понижения себя), сохранять полный доступ в обход текущей ролевой модели — нарушает принцип «одна проверка членства, без исключений». |
| Клиентское управление memberships (текущий legacy-подход через `authStore.inviteUser`/`updateUser`/`removeUser`) | Требует либо небезопасно широких Firestore Rules (как было до `BASE-004A`), либо оставляет привилегированные операции полностью неработающими (как сейчас, после emergency-патча) — ни один вариант не даёт одновременно безопасность и работоспособность без доверенного серверного посредника. |
| Глобальная роль пользователя для всех компаний | Противоречит требованию multi-company изоляции: пользователь, являющийся `admin` одной компании, не должен автоматически получать какие-либо права в другой — глобальная роль сделала бы это по построению. |

## Consequences

Принятие этой модели влечёт:

- **Дополнительные чтения membership.** Каждая операция, требующая
  проверки прав, обязана прочитать соответствующий документ
  `members/{companyId}/{uid}` — по сравнению с текущей моделью (один
  `users/{uid}` документ, часто уже загруженный в память), это
  дополнительный Firestore read на операцию (или Rules `get()`), что
  увеличивает как задержку, так и стоимость чтений.
- **Необходимость серверных функций.** Привилегированные операции
  (membership/role management, invitations, company deletion,
  last-admin-check) невозможны без Cloud Functions с Admin SDK — это
  новая инфраструктурная зависимость, отсутствующая в проекте сегодня
  (`SEC-003`).
- **Миграция legacy-данных.** Существующие пользователи и компании
  требуют backfill в новую подколлекцию `members` — риск некорректного
  переноса, требует dry-run/checksums/rollback (`SEC-005`).
- **Необходимость новых Rules и emulator-тестов.** Текущие emergency
  Rules (`BASE-004A`) не проверяют `members/*` вообще (коллекция не
  существует физически) — новые Rules и полный набор emulator-тестов по
  их сценариям потребуются отдельно (`SEC-003`/`SEC-011`).
- **Временная невозможность части клиентских administrative flows.**
  До появления backend (Cloud Functions) операции приглашения/смены
  роли/удаления участника/создания компании с назначением admin остаются
  недоступны клиенту напрямую — это уже так после `BASE-004A` и остаётся
  так до `SEC-003`.
- **Более строгая tenant isolation и fail-closed авторизация.** Прямое
  следствие «Security invariants» выше — ни один сценарий из
  `SECURITY_BASELINE.md` (self-escalation, cross-tenant read/write через
  подделанный `companyId`) структурно невозможен в целевой модели, а не
  просто заблокирован патчем поверх уязвимой архитектуры.

## Rollout dependencies

Целевая модель реализуется поэтапно следующими задачами — **ни одна из них
не выполняется в рамках `SEC-001`**:

- **`SEC-002`** — runtime-схемы (`src/schemas/auth.ts`, `src/schemas/company.ts`,
  обновление `src/types/auth.ts`) для валидации `Membership`/`UserProfile`/
  `Company` на границах приложения.
- **`SEC-003`** — серверные Cloud Functions и единые authz helpers:
  callable functions для invite/update-role/disable/remove membership,
  last-admin transaction-check, единая server-side проверка вместо
  разрозненной клиентской логики.
- **`SEC-004`** — серверное создание компании (замена сегодняшнего
  клиентского `setDoc(companies/{id})` + `setDoc(users/{uid}, {companies:
  [...]})` на доверенную серверную операцию, создающую и компанию, и
  первый `active admin` membership атомарно).
- **`SEC-005`** — backfill memberships: перенос существующих
  `users/{uid}.role`/`companyId`/`companies[]` в
  `companies/{companyId}/members/{uid}` с проверками идемпотентности.
- **`SEC-006`** — безопасные одноразовые приглашения: реализация сущности
  `invitations`, детальная схема принятия приглашения.
- Будущие Firestore Rules (реализуемые в рамках `SEC-003`/`SEC-011`)
  должны использовать `members` как единственный источник прав — этот ADR
  не заменяет и не изменяет действующие Rules сам по себе.
- Легаси-поля в `users/{uid}` нельзя удалять до завершения `SEC-005` и
  проверенного переключения чтения прав на `members`.
- **Emergency Rules (`BASE-004A`) остаются действующими** до отдельной
  задачи реализации и deployment новой постоянной модели — этот ADR не
  является триггером для их замены и не деплоит ничего сам по себе.
