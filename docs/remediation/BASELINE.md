### 8.2 Способ A — `git revert` (предпочтительный, не переписывает историю)

1. Определить коммит(ы), которые нужно откатить (то, что попало в `main`
   после последнего known-good состояния).
2. `git revert <sha>` (или `git revert <oldest>^..<newest>` для диапазона)
   в отдельной ветке от актуального `main`.
3. Получить разрешение владельца в формате `PRODUCTION_ACTION_APPROVED`
   (см. выше) — деплой возможен только через `push` в `main`.
4. После разрешения — `push` revert-коммита в `main`. Это автоматически
   запускает `.github/workflows/deploy.yml` (`push` → `branches: [main]`),
   job `build` (npm ci → lint → build) и затем `deploy` (условие
   `github.event_name == 'push' && github.ref == 'refs/heads/main'` —
   выполнится).
5. Дождаться завершения обоих jobs.

### 8.3 Способ B — повторный запуск известного успешного workflow run

1. Открыть конкретный прошлый успешный run (например,
   `https://github.com/Alexspb-spb1/finapp/actions/runs/27843178903`).
2. Выполнить «Re-run all jobs» (через GitHub UI или
   `actions_run_trigger` — оба варианта пересобирают и передеплоивают
   именно тот исходный код, на котором работал этот run, без нового
   commit/push).
3. Получить разрешение владельца (`PRODUCTION_ACTION_APPROVED`) перед
   фактическим запуском — это тоже production-деплой.
4. Дождаться завершения `build` и `deploy`.

Способ B быстрее и не создаёт новых коммитов, но результат «висит» на
старом коммите `main` без явного отражения в истории ветки — если нужен
самодокументируемый git-history откат, предпочтителен способ A.

### 8.4 Как проверить результат rollback

- Оба job (`build`, `deploy`) выбранного/нового run должны иметь
  `conclusion: success` — проверяется через `actions_get`/`actions_list`
  или вкладку Actions в GitHub UI.
- `head_sha` завершившегося `deploy`-run должен совпадать с ожидаемым
  known-good коммитом (см. 8.1) — не полагаться только на факт «run
  зелёный», а сверить именно SHA.
- Открыть `https://alexspb-spb1.github.io/finapp/` вручную в браузере и
  убедиться, что приложение загружается без JS-ошибок в консоли
  (страница логина — минимум, что доступно без реальных прод-Firebase-
  креденшалов в этой сессии).
- **Известное ограничение:** в приложении сейчас нет видимого индикатора
  версии/сборки (git SHA, номер релиза и т.п.) на самой странице — визуально
  отличить два соседних деплоя без разницы в UI/console нельзя. Это стоит
  учесть как отдельную находку для будущих задач (не в объёме `BASE-001`).

### 8.5 Условие, при котором rollback считается неуспешным

Rollback считается **неуспешным**, если выполняется любое из:

- job `build` или `deploy` завершился НЕ с `conclusion: success`
  (`failure`, `cancelled`, `timed_out` и т.п.);
- `deploy` job формально успешен, но `head_sha` соответствующего run не
  совпадает с ожидаемым known-good коммитом (значит, задеплоен не тот код);
- живой URL (`https://alexspb-spb1.github.io/finapp/`) недоступен
  (HTTP-ошибка/таймаут) более разумного времени ожидания после завершения
  `deploy` job;
- живой URL отвечает, но при открытии в браузере видны JS-ошибки в
  консоли, которых не было на known-good коммите (сравнение — вручную,
  автоматической regression-проверки консоли сейчас нет — появится в
  `TEST-001`/`IMP-008`);
- пользователь/владелец сообщает о видимой поломке функциональности,
  которой не было на known-good коммите, даже если сам деплой формально
  зелёный.

В любом из этих случаев — не пытаться «доткнуть» текущий rollback
дальнейшими правками; вернуться к последнему **независимо подтверждённому**
known-good состоянию (раздел 8.1) и эскалировать владельцу.
