## Краткое содержание принятого решения

Каноническая модель:

```text
companies/{companyId}
companies/{companyId}/members/{uid}
users/{uid}   — только глобальный профиль, НЕ источник прав
```

`companies/{companyId}/members/{uid}` — единственный источник авторизации:
`{ uid, role: 'viewer'|'accountant'|'admin', status:
'invited'|'active'|'disabled', createdAt, updatedAt, invitedBy? }`.

### Подтверждение выполнения всех десяти обязательных решений из плана

1. ID membership-документа == Firebase Auth UID — зафиксировано
   («Canonical data model» / инвариант 1).
2. Поле `uid` должно совпадать с ID документа — инвариант 2.
3. Авторизацию даёт только `status == 'active'` — инвариант 3.
4. `invited`/`disabled`/отсутствующий/повреждённый membership — всегда
   отказ — инвариант 4.
5. Неизвестная роль — всегда отказ — инвариант 5.
6. Отсутствие membership — всегда отказ — инвариант 6.
7. `createdAt`/`updatedAt` — управляются доверенным сервером — инвариант 7.
8. Клиент не может напрямую создавать/менять/удалять membership —
   инвариант 8.
9. Email/имя/`ownerId`/localStorage/переданный клиентом `companyId` — не
   доказательство членства — инвариант 9.
10. Роль не переносится из одной компании в другую — инвариант 10.

Дополнительно (обязательные пункты 5-13 задания SEC-001):
pre-acceptance invitation разрешён однозначно (отдельная будущая сущность
`invitations`, реальный UID обязателен, membership создаёт/активирует
сервер); last-admin инвариант и его атомарная серверная проверка описаны;
`ownerId` — справочная связь, не даёт доступа, требует отдельного `active
admin` membership для реальной работы; fail-closed требования перечислены
явно (список из задания воспроизведён дословно в разделе «Security
invariants» ADR); multi-company поведение зафиксировано (независимые
memberships, роль отдельно на компанию, отсутствие домашней роли,
изоляция при disable/удалении).

### Permission matrix (сводка — полная таблица в ADR)

| Ресурс | viewer | accountant | admin |
|---|---|---|---|
| Company metadata (чтение / запись) | allow / deny | allow / deny | allow / allow |
| Financial data, accounts, categories, transactions, projects/budgets (чтение / запись) | allow / deny | allow / allow | allow / allow |
| Closing period (запись) | deny | deny | allow |
| Member directory (чтение своей компании) | allow | allow | allow |
| Membership/role management | deny | deny | server-only |
| Company security settings | deny | deny | server-only |
| Invitations (создание/отзыв) | deny | deny | server-only |
| Invitations (принятие) | server-only | server-only | server-only |
| Audit events (чтение / запись) | deny / server-only | deny / server-only | allow / server-only |
| Company deletion | deny | deny | server-only |

Полная таблица со всеми 13 категориями ресурсов — в самом ADR, раздел
«Role and permission matrix».

### Явно отклонённые альтернативы

1. Роли внутри `users/{uid}` — смешивает профиль и авторизацию, источник
   текущей CRITICAL-уязвимости.
2. Массив `companies[]` как источник прав — та же проблема доверия
   клиентски-читаемому документу; плохо поддерживает атомарные Rules и
   server-managed таймстемпы на уровне отдельного membership.
3. Firebase custom claims как единственный источник часто меняющихся
   company memberships — требует принудительного обновления токена,
   несогласованность, лимит размера 1000 байт.
4. `ownerId` как авторизационный bypass — позволяет владельцу сохранять
   доступ в обход ролевой модели.
5. Клиентское управление memberships — либо небезопасно широкие Rules,
   либо (текущее состояние) нерабочие привилегированные операции.
6. Глобальная роль пользователя для всех компаний — противоречит
   multi-company изоляции.
