## Что изменено

### Канонические runtime-схемы — `src/schemas/auth.ts` (новый)
- `RoleSchema` — `z.enum(['viewer', 'accountant', 'admin'])`.
- `MembershipStatusSchema` — `z.enum(['invited', 'active', 'disabled'])`.
- `FirestoreTimestampSchema` — `z.instanceof(Timestamp)` (реальный класс
  `Timestamp` из `firebase/firestore`, не строка/число).
- `MembershipSchema` — точно по ADR-001: `uid`, `role`, `status`,
  `createdAt`/`updatedAt` (Timestamp), опциональный `invitedBy`. `.strict()`.
- `UserProfileSchema` — канонический профиль (`id`, `name`, `email`,
  `avatar?`, `createdAt`), `.strict()`, явно отклоняет
  `role`/`companyId`/`companies`/`isAdmin`/`permissions`.
- `LegacyUserSchema` — переходная схема текущего production-формата
  `users/{uid}` (см. «Canonical vs legacy» ниже).
- Callable-схемы: `CompanyScopedRequestSchema`, `MemberSubjectRequestSchema`,
  `SetMemberRoleRequestSchema`, `SetMemberStatusRequestSchema`,
  `MembershipResponseSchema`.
- Boundary-parsers: `parseUserProfileDocument`, `parseLegacyUserDocument`,
  `parseMembershipDocument`, плюс экспортируемый `zodIssuesToDataError`
  (переиспользуется в `company.ts`) и типы `DataError`/`ParseResult<T>`.

### `src/schemas/company.ts` (новый)
- `LegalTypeSchema` — `z.enum(['ooo', 'ip'])`.
- `CompanySchema` — точно по текущей production-форме (`id`, `name`,
  `legalType`, `inn?`, `currency`, `createdAt` как ISO-строка, `ownerId`),
  `.strict()`.
- Callable-схемы: `CreateCompanyRequestSchema`, `CreateCompanyResponseSchema`
  (использует `MembershipSchema` из `auth.ts` — единственная точка связи
  между файлами, без цикла: `company.ts` импортирует из `auth.ts`, не
  наоборот).
- Boundary-parser: `parseCompanyDocument`.

### `src/types/auth.ts` (изменён)
Типы `Role`, `MembershipStatus`, `Membership`, `UserProfile`, `User` —
`export type { ... } from '../schemas/auth'` (`z.infer`, не отдельно
написанные интерфейсы). `Company` — аналогично из `../schemas/company`.
`AuthSession` оставлен как есть (не является Firestore-документом/схемой
авторизации, вне scope). Используется `verbatimModuleSyntax`-совместимый
`export type {...} from`.

### `src/store/authStore.ts` (изменён)
- Убраны все 4 слепых приведения (список выше) — заменены на
  `parseLegacyUserDocument`/`parseCompanyDocument` и два новых локальных
  atomic-list-хелпера (`parseLegacyUsersList`, `parseCompanyDocsList`),
  гарантирующих «всё или ничего» для списков документов.
- Добавлено наблюдаемое состояние: `getAuthDataStatus()` →
  `'loading' | 'ready' | 'signed_out' | 'data_error'`, `getDataError()` →
  `DataError | null`.
- Новый общий обработчик `setDataErrorState(error)`: логирует только
  `source`/`issues` (без значений полей), очищает `currentUser`,
  `currentCompany`, `companyUsers`, выставляет `data_error`, вызывает
  подписчиков.
- `onAuthStateChanged`: реальный logout → `signed_out`; успешная
  recovery-ветка (не тронута по существу, только добавлена простановка
  `ready`) → `ready`; любая ошибка парсинга профиля/компании/списка
  пользователей/доп.компаний → `setDataErrorState(...)` и ранний `return`
  (не идёт дальше с частичными данными); непредвиденное исключение в `catch`
  → тоже `data_error` с непубличным `issues: ['unexpected_error']`.
- `switchCompany()`, `inviteUser()` — та же логика: парсер вместо cast,
  атомарный список, `data_error` при повреждении вместо частичного/подменённого
  результата. Бизнес-логика этих функций (что именно они делают и в каком
  порядке) не менялась — только замена приведения типа на проверку.
- `register()` — добавлена простановка `authDataStatus = 'ready'` после
  успешной оптимистичной записи (не меняет саму логику регистрации).

### `src/hooks/useAuth.ts` (изменён)
Добавлены `status` и `dataError` в возвращаемый объект. При
`status === 'data_error'`: `isAuthenticated = false`, `readOnly = true`,
`canWrite = false`, `isAdmin = false` — независимо от того, что вернул
`getEffectiveRole()` для уже очищенного `currentUser`.

## Canonical vs legacy — явное разделение

`LegacyUserSchema` — **переходная**, не каноническая модель авторизации:
- используется только для проверки текущего старого формата
  `users/{uid}` (`role`/`companyId`/`companies[]` внутри профиля) до
  выполнения backfill в `SEC-005`;
- остаётся строгой: неизвестная роль (домашняя или внутри `companies[]`),
  отсутствующий `companyId`, повреждённый элемент массива, лишнее поле —
  всё отклоняется; никаких default/fallback значений;
- канонический `UserProfileSchema` **отклоняет** валидный legacy-документ
  целиком (тест `rejects a legacy document shape outright`) — два контракта
  осознанно несовместимы, чтобы легаси-поля не могли случайно "просочиться"
  как будто они часть канонической модели;
- `authStore.ts` сегодня использует **только** `parseLegacyUserDocument`
  (реальные production-документы — по-прежнему legacy-формат;
  `parseUserProfileDocument`/`UserProfileSchema` пока нигде не вызываются
  на реальных данных — они готовы к использованию будущими `SEC-003+`
  задачами, когда появится сервер, пишущий канонический профиль).
- фактическая авторизация **не переключена** на membership-модель:
  коллекция `companies/{companyId}/members/{uid}` не существует ни в
  Rules, ни в реальных данных — она появится в `SEC-003`–`SEC-005`.

## Форма `data_error`
```ts
interface DataError {
  code: 'data_error'
  source: string     // напр. "users/{uid} (legacy)", "companies/{companyId}"
  issues: string[]    // напр. ["role: invalid_value", "id: document_id_mismatch"]
}
```
`issues` содержит только `path`+`code` каждого проблемного поля Zod-ошибки —
никогда `.message` (может отличаться по версии/локали) и никогда исходное
значение поля. Подтверждено тестами `error object never contains the source
document values` (оба файла схем) и `data_error never logs the corrupted
document values` (authStore-тест, проверяет реальные вызовы `console.error`).

## Поведение authStore при повреждённом документе
- Не использует повреждённые данные ни частично, ни полностью.
- Не подставляет `viewer`/`accountant`/`admin` по умолчанию — неизвестная
  роль отклоняется schema-уровнем раньше, чем authStore успевает её увидеть.
- Не продолжает с частично загруженным списком — `parseLegacyUsersList`/
  `parseCompanyDocsList` фейлят весь список при первой же повреждённой
  записи (тест `a list of company users with ONE corrupted record fails
  atomically`).
- Очищает `currentUser`, `currentCompany`, `companyUsers` — не оставляет
  предыдущего успешного (потенциально более привилегированного) состояния
  висеть при последующей ошибке.
- Выставляет типизированный `data_error` (`getAuthDataStatus()`/`getDataError()`).
- Вызывает подписчиков (`notify()`), чтобы UI-хук (`useAuth`) не завис в
  `loading`.
- Не записывает повреждённый документ обратно в Firestore — `authStore.ts`
  ни в одном из изменённых путей не выполняет `setDoc`/`updateDoc` с
  необработанными сырыми данными снапшота.
- Не раскрывает содержимое документа в `console` — только `source`+`issues`
  (path/code), см. выше.

## Security review
- Ни одна схема не использует `.passthrough()` на авторизационных объектах —
  все `.strict()`.
- Ни одна схема не использует `.default()`/`.catch()`/`coerce` для
  `role`/`status` — неизвестное значение всегда `ZodError` → `data_error`.
- `FirestoreTimestampSchema` требует реальный `Timestamp`-инстанс — строка
  или число никогда не проходят (тесты `rejects a string/number in place of
  a Firestore Timestamp`).
- `zodIssuesToDataError` использует только `path`+`code` каждого issue —
  никогда `.message`, никогда значение поля — подтверждено тестами,
  проверяющими `JSON.stringify(error)` на отсутствие secret/email-подобных
  значений.
- Document-ID проверяется отдельно от содержимого документа во всех трёх
  parsers (`parseUserProfileDocument`, `parseLegacyUserDocument`,
  `parseMembershipDocument`, `parseCompanyDocument`) — несовпадение всегда
  `data_error`.
- `ownerId` в `CompanySchema` валидируется только как непустая строка —
  не превращается ни в какое авторизационное поле (тест `ownerId is
  validated as a plain string reference, never turned into a role/admin
  field`).
- `authStore.ts`: ни один путь не пишет непроверенные сырые данные обратно
  в Firestore; ни один путь не логирует содержимое документа/email —
  только `source`+`issues`.
