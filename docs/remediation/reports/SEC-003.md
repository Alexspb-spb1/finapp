## Как в реальности были написаны тесты (без искажений)

Это описание не соответствует классическому TDD/"red-first" — фиксируется
честно, как есть:

1. Сначала была написана вся серверная реализация
   (`functions/src/lib/*.ts`, `functions/src/schemas/auth.ts`,
   `functions/src/index.ts`) **и** весь набор тестов
   (`functions/test/unit/*.test.ts`, `functions/test/emulator/*.test.ts`)
   в рамках одной непрерывной сессии разработки — тесты не были написаны и
   запущены против отсутствующей реализации ДО того, как реализация была
   создана.
2. После того как обе стороны (реализация и тесты) уже существовали,
   выполнена **post-implementation stub mutation-проверка**: реализация
   пяти файлов (`src/lib/errors.ts`, `src/lib/authz.ts`,
   `src/lib/idempotency.ts`, `src/lib/audit.ts`, `src/index.ts`) была
   временно заменена на пустые заглушки (`export {}`), после чего выполнен
   `npm run test:unit --prefix functions`.
3. Результат прогона против заглушек: **36 из 40** unit-тестов упали
   (`TypeError: X is not a function` / отсутствующий экспорт для каждого
   импортированного из заглушённых модулей символа); 4 теста
   (не зависящие от заглушённых модулей) прошли без изменений.
4. Реализация была восстановлена из резервной копии (см. «Известные
   ограничения» — файлы временно копировались в scratch-каталог сессии, не
   в репозиторий), после чего:
   - `npm run test:unit --prefix functions` → **40/40 PASS**;
   - `npm run test:emulator --prefix functions` (реальный Functions
     Emulator + Auth Emulator + Firestore Emulator, `--project demo-finapp`)
     → **28/28 PASS**.
   - Итого **68** тестов пакета `functions/` (40 unit + 28 emulator),
     все зелёные после восстановления реальной реализации.

Это правильно называть **post-implementation mutation-проверкой**
(разновидность мутационного тестирования: «если стереть реализацию, тесты
обязаны упасть») — она подтверждает, что тесты не тривиально проходят
независимо от кода, но это **не** red-first/TDD-red в строгом смысле
(тесты и код создавались параллельно/последовательно в одной сессии, а не
тесты → красный прогон → написание кода). Красное состояние (заглушки) не
коммитилось — реализация восстановлена перед любым коммитом.

### Почему схемы не импортируются из `src/schemas/`
`functions/` — отдельный deployable npm-пакет со своим деревом зависимостей
(Admin SDK, Node 22 runtime, свой `package-lock.json`). Кросс-пакетный
импорт TS-исходников из корневого `src/` создал бы скрытую сборочную
связь между клиентским и серверным деплоями и потребовал бы либо monorepo
workspace tooling (не запрошено, `ROOT_DEPENDENCY_UPDATE_APPROVED: false`),
либо копирования `zod`-версии корня. Вместо этого `functions/src/schemas/auth.ts`
— самостоятельная копия, синхронизируемая по контракту (ADR-001 +
`docs/remediation/reports/SEC-002.md`/`SEC-003.md`), а не по общему
исходнику. Это сознательный компромисс, зафиксированный как известное
ограничение ниже.

## Authz flow (`functions/src/lib/authz.ts`)

Единая последовательность для `authzProbe` (и образец для будущих
привилегированных команд `SEC-004`+):

```text
requireAuth(request)               — источник identity ТОЛЬКО request.auth (никогда payload.uid)
  → requireVerifiedEmail(auth)     — ТОЛЬКО auth.token.email_verified === true
  → validateRequest(schema, data)  — строгая Zod-схема, лишние поля отклоняются
  → requireActiveMember(db, companyId, uid)
                                    — читает РОВНО companies/{companyId}/members/{uid};
                                      MembershipSchema; document ID == membership.uid;
                                      status === 'active'; иначе — deny
  → requireRole(membership, ['admin'])
                                    — allowlist ролей; неизвестная роль уже отсеяна схемой
```

`requireActiveMember` фейлит closed при: отсутствующем документе
(`membership_not_found`), `invited`/`disabled` (`membership_inactive`),
неизвестной роли/статусе/повреждённом документе (`membership_data_error`),
несовпадении document ID и `membership.uid` (`membership_data_error`),
**и** при ошибке чтения Firestore (`membership_data_error` — перехвачено
try/catch, ошибка никогда не пробрасывается наружу как есть).

## Last-admin design (`assertNotLastAdmin`)

Выполняется **внутри той же** Firestore `Transaction`, что и будущая
мутация (сначала `await assertNotLastAdmin(db, txn, companyId, subjectUid)`,
затем `txn.update/delete(...)` в том же `runTransaction`-callback). Запрос
активных админов выполняется через `txn.get(query)`, а не отдельный
`.get()` — поэтому конкурирующая транзакция, изменившая любой документ из
результата этого запроса, инвалидирует read-set и вызывает retry с уже
актуальными данными (нативный механизм Firestore optimistic concurrency).
`ownerId` нигде не участвует в проверке (справочное поле, см. ADR-001).

## Idempotency design (`functions/src/lib/idempotency.ts`)

Receipt (`fingerprint` + `result`) и бизнес-мутация пишутся **одним и тем
же** `run()`-callback внутри **одной** `db.runTransaction(...)` — без
отдельной фазы «отметить in_progress → выполнить → отметить done».
Сырой `idempotencyKey` никогда не используется как путь напрямую — всегда
хешируется вместе с `{operation, companyId, callerUid}`
(`sha256`), что одновременно валидирует безопасность как пути и как
scope-изоляции. Fingerprint — `sha256` от детерминированно
key-sorted JSON тела запроса (не зависит от порядка ключей). Явно
задокументировано: внешние сетевые side-effects внутри `run()` этим
механизмом не защищены.

## Audit design (`functions/src/lib/audit.ts`)

`writeAuditEvent(db, writer, input)` — `writer: Transaction | WriteBatch`,
вызывающий обязан передать ТУ ЖЕ транзакцию/batch, что и сама мутация
(атомарность подтверждена тестом на rollback — см. «Тесты»). Поля:
`action`, `actorUid` (обязан быть `request.auth.uid`, не из payload),
`targetUid` (опционально), `metadata` (безопасный объект), `createdAt`
(`FieldValue.serverTimestamp()`). Сырое тело запроса, токены, пароли —
не сохраняются ни при каких условиях (сама структура типа `AuditEventInput`
их не допускает).

## Конфигурационные исправления, обнаруженные и внесённые в процессе
1. **`functions/vitest.config.ts` → `functions/vitest.config.mts`** — исходный `.ts`
   с ESM `import`-синтаксисом внутри CommonJS-пакета (`functions/package.json`
   без `"type": "module"`) вызывал предупреждение Vite/Vitest о смешении
   ESM/CJS (`configLoader: 'native'`). Переименование в `.mts` устраняет
   предупреждение без изменения поведения теста.
2. **`functions/eslint.config.js` → `functions/eslint.config.mjs`** — та же
   причина: ESLint явно предупреждал (`MODULE_TYPELESS_PACKAGE_JSON`) о
   парсинге `.js`-файла с ESM-синтаксисом как CJS. Переименование в `.mjs`
   устраняет предупреждение.
3. **`functions/tsconfig.json`: `moduleResolution: "node"` → добавлен
   `"ignoreDeprecations": "6.0"`** — TypeScript 6 помечает
   `moduleResolution=node` (алиас `node10`) как deprecated (`TS5107`,
   станет ошибкой в TS7). Опробован переход на `"module"/"moduleResolution":
   "Node16"` — это привело к НОВОЙ ошибке компиляции (`TS2349`, union-тип
   `Transaction | WriteBatch` перестал вызываться через `.set()` из-за
   несовместимых перегрузок при более строгом резолвинге типов). Переход
   на Node16 отменён; вместо него оставлен проверенный `moduleResolution:
   "node"` с явным `ignoreDeprecations: "6.0"` — осознанное решение
   остаться на стабильной, полностью работающей конфигурации, а не гнаться
   за устранением одного предупреждения ценой новой ошибки.
4. **`functions/src/lib/audit.ts` — union-type fix**: `writer.set(ref, data)`
   с `writer: Transaction | WriteBatch` не компилировался (`TS2349`,
   несовместимые перегрузки `.set()` у двух типов при объединении в union).
   Исправлено введением локального минимального структурного интерфейса
   `SetCapableWriter { set(ref, data): unknown }`, которому оба типа
   удовлетворяют структурно — без `any`, без ослабления типобезопасности
   вызывающего кода (`writer: Transaction | WriteBatch` в сигнатуре
   `writeAuditEvent` не изменился).

## Security review
- Ни один helper не использует `users/{uid}.role`, `ownerId`, localStorage
  или client state как источник прав — единственный источник:
  `companies/{companyId}/members/{uid}` через `requireActiveMember`.
- `requireAuth`/`requireVerifiedEmail` используют исключительно
  платформенно-проверенный `request.auth`/`request.auth.token` — payload
  никогда не консультируется как источник identity (подтверждено тестом
  «never consults a uid field inside the payload as identity» и emulator-
  тестом «a spoofed uid field in the payload is rejected as invalid_request»).
- `validateRequest` — строгие Zod-схемы, лишние поля (`role`, `isAdmin`,
  `permissions`, поддельный `uid`) отклоняются целиком как `invalid_request`
  раньше, чем запрос доходит до membership-проверки.
- `assertNotLastAdmin` доказано транзакционно-безопасным через
  параллельный emulator-тест (`Promise.all` двух конкурентных demote-
  запросов): ровно один успевает, второй получает `last_admin`, финальное
  состояние — минимум один active admin.
- Ошибки, возвращаемые клиенту, и всё, что попадает в `console.*`,
  проверены на отсутствие secret-like значений (companyId/uid/email/
  invitedBy) — unit- и emulator-тестами с уникальными синтетическими
  «секретами», которых заведомо нет ни в одном другом тесте/файле
  репозитория.
- `npm ci` внутри `functions/` использует `functions/package-lock.json` —
  никаких неожиданных транзитивных обновлений (лок-файл закоммичен как
  сгенерирован при первой установке, не редактировался вручную).

## Известные ограничения
- **Синхронизация схем вручную.** `functions/src/schemas/auth.ts` — не
  импорт из `src/schemas/auth.ts`, а независимая копия по контракту (см.
  «Архитектура Functions»). Расхождение между копиями при будущих
  изменениях ADR/контракта не будет поймано компилятором — только review/
  тестами. Зафиксировано как явный компромисс, не случайный недосмотр.
- **`npm ci --prefix functions` не переустанавливался на финальном шаге.**
  По прямому указанию в рамках этой сессии повторная установка не
  запускалась — использовалось уже установленное дерево
  `functions/node_modules` (актуальность package-lock.json проверена
  командой `npm ls firebase-admin firebase-functions zod` — версии
  совпадают с задекларированными в `functions/package.json`). Полная
  холодная установка (`npm ci`) из этого же `package-lock.json` явно
  прогоняется в CI job `functions` (см. `.github/workflows/ci.yml`) —
  будет независимо подтверждена там.
- **Node 22 — портативная установка только для этой сессии.** Не изменяет
  системный Node, не влияет на root-проект (Node 24.16.0 остаётся
  системным/используемым для root-проверок). CI job `functions` использует
  `actions/setup-node@v4` с `node-version-file: functions/.nvmrc` —
  независимая, воспроизводимая установка Node 22 в CI, не зависящая от
  этой сессии.
- **`npm audit` — известная нестабильность во времени**, задокументирована
  выше с двумя внутрисессионными снятиями показаний (18 → 19) без единого
  изменения зависимостей.
- **Идемпотентность не покрывает внешние сетевые side-effects** — явно
  описано как ограничение в самом `idempotency.ts` и в этом отчёте; не
  относится к текущему scope (нет ни одной функции, вызывающей внешние
  API).
- **Ни одна мутирующая привилегированная функция не существует** — это
  ожидаемая граница `SEC-003` (только authorization foundation), а не
  недоделанная работа; `SEC-004`+ реализуют реальные команды поверх этих
  helpers.
