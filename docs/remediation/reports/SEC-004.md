## Исправления по итогам независимого аудита (PR #12)

Ниже — все 6 блокирующих замечаний независимого аудита и как каждое исправлено. Base для этого раунда — ранее проверенный head `30cf8c4` (см. выше); все изменения — новый единственный коммит `fix(sec-004): make company bootstrap safely resumable`.

### 1. Преждевременное удаление pending-состояния
**Было:** `authStore.completeCompanySetup()` вызывал `clearPendingSetup()` сразу после успешного ответа `createCompany`, ДО чтения/валидации `users/{uid}` и `companies/{companyId}`. Временный сбой чтения Firestore после успешного серверного commit терял pending-состояние безвозвратно, и `activeCompanyId` фиксировался как активный до подтверждения.

**Исправлено** (`src/store/authStore.ts`):
- `loadReadyStateAfterSetup()` теперь возвращает три исхода — `'ready' | 'transient_failure' | 'data_error'` (было `boolean`).
- `completeCompanySetup()` вызывает `clearPendingSetup()` и фиксирует `activeCompanyId`/`localStorage` ТОЛЬКО при `'ready'`.
- При `'transient_failure'` pending-состояние сохраняется (тот же `idempotencyKey`), `authDataStatus` → `'setup_incomplete'`.
- При `'data_error'` — `loadReadyStateAfterSetup()` уже вызвал `setDataErrorState()` с реальной ошибкой; `completeCompanySetup()` эту `authDataStatus` больше НЕ перезаписывает `'setup_incomplete'`.
- Сетевая/серверная ошибка самого `callCreateCompany()` (catch-блок) тоже больше не вызывает `clearPendingSetup()`.

**Новый red→green тест** (`src/store/authStore.createCompany.test.ts`, описание `authStore.completeCompanySetup — независимый audit fix #1`): `callable success -> Firestore read failure -> setup_incomplete -> retry with same key -> canonical load success` — воспроизводит ТОЧНЫЙ сценарий из задания; плюс отдельные тесты на `activeCompanyId` (не фиксируется до `'ready'`) и на то, что реальный `data_error` не перезаписывается.

### 2. Восстановление после reload/login
**Было:** `ProtectedRoute` при `!isAuthenticated` всегда редиректил на `/login`; авторизованный, но незавершённый пользователь при повторном логине снова получал `signInWithEmailAndPassword` успех → `navigate('/')` → `ProtectedRoute` снова редиректил на `/login` (видимый цикл `/ → /login` без выхода). `Register.tsx` не умел показать `setup_incomplete` при заходе НЕ через саму форму регистрации (например, после reload/редиректа).

**Исправлено**:
- **`src/components/layout/resolveProtectedRouteRedirect.ts`** (новый файл — чистая функция без React/Firebase-импортов, чтобы избежать `react-refresh/only-export-components` и остаться тестируемой без jsdom): при `!isAuthenticated && status === 'setup_incomplete'` возвращает `/register`, а не `/login`. `ProtectedRoute.tsx` — точечная правка (единственная строка логики редиректа заменена на вызов этой функции), никакой другой UI не тронут.
- **`Login.tsx` НЕ изменялся** — минимальный вариант оказался достаточным только через `ProtectedRoute`.
- **`src/pages/Register.tsx`**: `step` инициализируется из `authStore.getAuthDataStatus()` при монтировании и синхронизируется через `subscribeAuth()` — так экран `setup_incomplete` появляется при заходе после reload/редиректа, а не только сразу после `handleSubmit`.
- Новый `authStore.startCompanySetup()` — для случая, когда pending-состояние недоступно (`localStorage` очищен/другое устройство): позволяет заново ввести имя/данные компании и завершить настройку БЕЗ повторного `createUserWithEmailAndPassword` и без пароля. `Register.tsx` показывает эту мини-форму вместо кнопки «Повторить», когда `authStore.getResumableSetupSummary()` возвращает `null`.

**Новые тесты**: `src/components/layout/resolveProtectedRouteRedirect.test.ts` (5 тестов, чистая логика, без DOM) + `authStore.startCompanySetup` describe-блок (4 теста: не вызывает `createUserWithEmailAndPassword`, повторный вызов не плодит второй Auth-аккаунт, `getResumableSetupSummary` возвращает `null`/сводку) + тест «после симулированного reload (свежая загрузка модулей) тот же uid снова находит своё resumable pending-состояние».

### 3. Pending setup не был привязан к UID
**Было:** `PendingCompanySetup` не содержал `uid` — на общем устройстве pending-состояние пользователя A могло быть подхвачено пользователем B при вызове `completeCompanySetup()`.

**Исправлено** (`src/store/authStore.ts`): `PendingCompanySetup.uid` — обязательное поле, проставляется из `cred.user.uid`/`auth.currentUser.uid` при сохранении. Новая `loadUsablePendingSetup(uid)` возвращает pending ТОЛЬКО если `pending.uid === uid`; `completeCompanySetup()` использует исключительно её. При несовпадении `callCreateCompany` не вызывается вообще, возвращается `setup_incomplete`, чужие имя/ИНН/данные компании никогда не отправляются.

**Новый тест**: «a pending setup for uid A cannot be resumed as uid B (shared-device isolation)» — регистрирует A (ошибка, pending сохранён), затем меняет текущего пользователя на B и вызывает `completeCompanySetup()`; проверяет, что `callCreateCompany` НЕ вызывается второй раз.

### 4. Bootstrap не был защищён от существующих пользователей
**Было:** `runBootstrapIdempotent()`/`createCompany` проверяли только receipt `user_bootstrap/{uid}`; пользователь с уже существующим `users/{uid}` (например, legacy-аккаунт до SEC-004, или созданный через `authStore.inviteUser`), но без receipt, мог получить вторую «первую» компанию, а его `users/{uid}` — быть перезаписан.

**Исправлено** (`functions/src/index.ts`): первым действием внутри `run()` (та же транзакция, что и receipt-проверка) читается `users/{uid}`; если документ существует — `throw new AppError('idempotency_conflict')` до какого-либо `txn.set()`. Стабильный код ошибки без пользовательских данных; исходный профиль не читается-перезаписывается, компания/членство/company_data/receipt/audit не создаются.

**Новый real-emulator-тест** (`functions/test/emulator/createCompany.test.ts`): «a uid with an EXISTING users/{uid} profile but no bootstrap receipt is rejected» — сидирует legacy-профиль (с `companies[]`, `avatar`, чужим `companyId`) напрямую через Admin SDK, вызывает `createCompany` с новым ключом, проверяет `idempotency_conflict`, что профиль побайтово не изменился (`toEqual`), и что не создано ни одной компании/receipt. Это одновременно и требуемое доказательство «ошибка внутри транзакции не оставляет частичных документов» — throw происходит после вычисления `companyRef`/`membershipRef`/`companyDataRef`, но до первого `txn.set()`.

## Что изменено

### Backend (`functions/`)
- **`functions/src/schemas/company.ts`** (новый) — `CreateCompanyRequestSchema` (`.strict()`, `idempotencyKey`/`ownerName`/`companyName` non-empty-after-trim, `legalType: 'ooo'|'ip'`, `inn` опционален и валидируется под конкретный `legalType` — 10 цифр для `ooo`, 12 для `ip`) и `CreateCompanyResponseSchema` (`{ companyId }` — ничего больше).
- **`functions/src/lib/bootstrapIdempotency.ts`** (новый) — узкий bootstrap-идемпотентный механизм для «первой компании» пользователя, отдельный от `runIdempotent()` (который привязан к уже существующему `companyId` и не трогается/не ослабляется). Receipt хранится по фиксированному пути `user_bootstrap/{uid}`, ключ — **только uid**, не сырой idempotency key — это и есть механизм, которым «один uid не может создать две первые компании даже с разными ключами» (см. «Архитектура» ниже). Переиспользует `computeFingerprint`/`validateIdempotencyKey` из `idempotency.ts` (последняя сделана `export`, поведение не изменено).

## Архитектура `createCompany`

**Request** (`CreateCompanyRequestSchema`, `.strict()`):
```ts
{ idempotencyKey: string; ownerName: string; companyName: string; legalType: 'ooo'|'ip'; inn?: string }
```
`uid`/`ownerUid`/`role`/`companyId`/`createdAt`/`currency` и любые другие поля — отклоняются схемой целиком (лишние ключи → `invalid_request`, значение никогда не попадает в текст ошибки — переиспользован существующий `validateRequest()`/`AppError`, который не имеет параметра details).

**Response**: `{ companyId: string }` — ничего больше.

**Источник каждого привилегированного значения**:
| Поле | Источник |
|---|---|
| `uid` (owner/admin) | `requireAuth(request).uid` — платформенно-верифицированный ID-токен |
| `email` | `adminAuth.getUser(auth.uid).email` (Admin Auth), никогда payload |
| `companyId` | `db.collection('companies').doc().id` — случайный Firestore ID, генерируется сервером |
| `role` (membership) | жёстко `'admin'` в коде — не из payload |
| `createdAt`/`updatedAt` (membership) | `FieldValue.serverTimestamp()` |
| `name`/`legalType`/`inn` (company) | из провалидированного payload (не привилегированные — контролируются самим создателем) |

**Bootstrap-идемпотентность** (`functions/src/lib/bootstrapIdempotency.ts`) — receipt по фиксированному пути `user_bootstrap/{uid}` (ключ — **только uid**, не сырой idempotency key):
- Тот же key + тот же fingerprint payload → возвращается закэшированный `{companyId}`, мутация не повторяется.
- Тот же key + другой payload → `idempotency_conflict`.
- **Другой** key для того же uid → тоже `idempotency_conflict` — потому что receipt лежит по uid, а не по хешу ключа: второй вызов читает ТОТ ЖЕ документ и видит, что `stored.idempotencyKey !== idempotencyKey`. Это и есть требуемое «один uid не может создать две первые компании даже с разными ключами».
- Receipt и бизнес-мутация пишутся ОДНИМ `run()` внутри ОДНОЙ `db.runTransaction()` — тот же однофазный паттерн, что и у `runIdempotent()`, без промежуточного «in_progress» состояния.
- Конкурентность: обе параллельные транзакции читают `user_bootstrap/{uid}` в свой read set; Firestore optimistic concurrency заставляет проигравшую транзакцию повторно выполниться и увидеть уже закоммиченный receipt — тот же механизм, на котором держится `assertNotLastAdmin()` из SEC-003. Подтверждено эмулятор-тестами (`Promise.allSettled` на двух параллельных вызовах — ровно один company).

**Список создаваемых документов** (все — одной транзакцией):
```text
companies/{companyId}
companies/{companyId}/members/{uid}
company_data/{companyId}
users/{uid}                       — временный совместимый bridge, см. ниже
user_bootstrap/{uid}              — bootstrap-идемпотентный receipt
companies/{companyId}/audit_events/{autoId}  — через существующий writeAuditEvent()
```

## Ограничение `users/{uid}` compatibility bridge
Сервер по-прежнему пишет `users/{uid}` в минимальной legacy-совместимой форме (`{id, name, email, role: 'admin', companyId, createdAt}`), т.к. клиентский `parseLegacyUserDocument`/`LegacyUserSchema` (SEC-002) и большая часть `authStore.ts` (`onAuthStateChanged`, `getEffectiveRole()`, `switchCompany()`, страница «Пользователи») всё ещё читают роль/companyId именно оттуда. Это временный **серверный** мост — клиент сам это поле больше не пишет и не может (Firestore Rules `users/{userId}` create по-прежнему запрещают `role`/`companyId`/`companies` в клиентской записи; Admin SDK эти Rules не проходит, так что сервер может писать поле, которое клиенту запрещено). Каноническим источником авторизации остаётся `companies/{companyId}/members/{uid}` (ADR-001). Полное удаление legacy-полей из `users/{uid}` и client-side чтения — SEC-005/SEC-008.

- **Атомарность** — вся мутация (company/membership/company_data/users-bridge/receipt/audit) — одна Firestore-транзакция; невалидные данные или конфликт идемпотентности не оставляют частичных документов (проверено emulator-тестами прямым чтением через Admin SDK).
- **requireVerifiedEmail сознательно не вызывается** здесь — задокументированное bootstrap-исключение (иначе только что созданный пользователь не смог бы зарегистрировать компанию вообще, т.к. email ещё физически не мог быть подтверждён). Обязательное принудительное применение — SEC-013. Письмо верификации всё равно отправляется.
- **Firestore Rules не менялись** — `users/{userId}` create по-прежнему запрещает клиенту писать `role`/`companyId`/`companies` (Admin SDK, которым пишет `createCompany`, эти Rules не проходит — ожидаемо и безопасно, т.к. только серверный код имеет Admin-доступ).

## Известные ограничения
- **`users/{uid}` legacy compatibility bridge** остаётся (см. раздел выше) — полное устранение legacy-полей и client-side чтения роли из `users/{uid}` — **SEC-005**. (Теперь этот bridge дополнительно защищён guard'ом из audit fix #4 — существующий `users/{uid}` без bootstrap receipt больше не может быть перезаписан повторным bootstrap-вызовом.)
- **`onAuthStateChanged`'s "companies/{companyId} missing" recovery-ветка** (для СУЩЕСТВУЮЩЕГО профиля с висячим `companyId`, не для регистрации) не тронута — по-прежнему создаёт `companies/{companyId}`/`company_data/{companyId}` с клиента при отсутствии документа компании. Это отдельный fail-open путь, не входящий в явный список SEC-004/замечаний аудита (который про создание компании ПРИ РЕГИСТРАЦИИ) — рекомендуется **SEC-005/SEC-008**.
- **`authStore.createCompany()`** (добавление ДОПОЛНИТЕЛЬНОЙ компании существующим авторизованным пользователем — multi-company flow, отдельная кнопка в UI, не регистрация) по-прежнему пишет `companies`/`company_data` напрямую с клиента; Firestore Rules это по-прежнему разрешают (`allow create: if isSignedIn() && ...`). Не входит в текст SEC-004/замечаний аудита, но представляет тот же класс риска — рекомендуется отдельная задача **SEC-005**.
- **`requireVerifiedEmail` не применяется** к `createCompany` — осознанно, обязательное применение отложено до **SEC-013**.
- **UI-уровневый пробел частично сохраняется**: логика редиректа (`resolveProtectedRouteRedirect`) и логика восстановления регистрации (`resolveRegistrationRecovery`, раунд №2) теперь покрыты чистыми unit-тестами, но JSX-рендеринг `Register.tsx`/`ProtectedRoute.tsx` (т.е. что реальный клик по кнопке действительно вызывает нужный обработчик, что `<Navigate>`/`navigate('/')` действительно вызывается в реальном DOM) по-прежнему проверен только **ревью кода**, а не component-тестом — в репозитории нет React Testing Library/jsdom-инфраструктуры, и добавление такой инфраструктуры — вне минимального scope этой задачи (запрещено добавлять непрофильные devDependencies без прямой необходимости). Вся ЛОГИКА принятия решений (что вызывается и когда, включая переход `setup_incomplete → ready → navigate_home` после reload) при этом вынесена в чистые функции и покрыта тестами напрямую — это и был предмет второго раунда исправлений, закрывший ранее упущенный сценарий reload-восстановления.
- `npm audit` (root и functions) показывает baseline-уязвимости, идентичные зафиксированным ранее — ни первоначальная реализация SEC-004, ни этот раунд исправлений не добавили новых зависимостей.
