   строятся через `String.fromCharCode(58, 58)` (символ `::`) —
   детерминированно, без риска скрытого символа — и весь код-потребитель
   (`legacyMapping.ts`, `firestoreReaders.ts`, `backfill-memberships.ts`,
   тесты) переведён на них вместо ручного построения ключей через шаблонные
   строки.
2. Баг last-admin-гейта — исходная реализация `buildPlan()` включала
   `companyId` каждого **orphan** (ссылка на несуществующую компанию) в
   множество компаний, проверяемых на «есть ли admin», из-за чего тест
   «an unresolved orphan blocks apply until acknowledged via an exclude
   decision» **реально проваливался** (`applyAllowed` оставался `false`
   даже после подтверждающего decision). Исправлено: гейт теперь построен
   только по компаниям с хотя бы одной **подтверждённой** (после decisions)
   relation — несуществующая компания никогда не участвует в проверке
   «есть ли у неё admin», что и логически корректно (проверять наличие
   admin у компании, которой нет, бессмысленно).

Оба бага были обнаружены реальными прогонами `npx vitest run scripts` в ходе
разработки этой ветки и исправлены до финализации коммита — сами тесты,
зафиксировавшие их, сохранены без изменений и проходят зелёным в финальном

## Матрица конфликтов/orphan/owner-anomaly

| Тип | Условие | Куда попадает | Может ли decision разрешить |
|---|---|---|---|
| `role_mismatch` | 2+ различных ВАЛИДНЫХ роли для одной пары | conflicts | `confirm_role`/`exclude` |
| `invalid_role` | Все claims для пары — неизвестная/пустая/битая роль | conflicts | `confirm_role`/`exclude` |
| `user_id_mismatch` | `users/{uid}.id` присутствует и ≠ ID документа | conflicts (для ВСЕХ relations этого документа) | `confirm_role`/`exclude` |
| `owner_role_not_admin` | `ownerId` имеет подтверждённую НЕ-admin роль | conflicts | `confirm_role`/`exclude` |
| `existing_membership_conflict` | Существующий `members/{uid}` не совпадает с кандидатом | conflicts | только `accept_existing` |
| `missing_company` | legacy-поле ссылается на несуществующую компанию | orphans | только `exclude` (никогда `confirm_role` — decision не может создать компанию) |
| `missing_user` | `ownerId` ссылается на несуществующего пользователя | orphans | только `exclude` |
| `owner_without_admin_membership` | `ownerId` без какого-либо membership claim | ownerAnomalies | `confirm_role`/`exclude` |

## Security review

- **Fail-closed везде**: неизвестная/пустая/битая роль никогда не получает
  default; отсутствующий документ никогда не подразумевает `admin`;
  `ownerId` — только сигнал для проверки, никогда прямой источник admin.
- **Create-only writes**: `DocumentReference.create()` — Admin SDK сам
  обеспечивает precondition «документ отсутствует»; race между planning и
  apply не может привести к тихой перезаписи.
- **Никаких credentials в коде/логах**: `initFirestore()` никогда не читает
  service-account JSON вручную — делегирует ADC resolution целиком Admin
  SDK; stdout содержит только safe aggregates (project ID, mode, checksums,
  counts) — проверено `printSafeSummary()`, отдельно от полного отчёта.
- **PII вне Git**: полный отчёт и decisions-файл принудительно проверяются
  на абсолютный путь ВНЕ репозитория (`assertSafeReportPath()`) —
  зафиксировано тестом.
- **Project guard до I/O**: несовпадение CLI/env project ID отклоняется до
  `initFirestore()` — подтверждено real-emulator тестом (report не создаётся
  вообще).

## Исправления по итогам независимого аудита

Независимый ревьюер вернул `REVIEW_RESULT: CHANGES REQUIRED` с 7 категориями
блокирующих замечаний по исходной реализации (см. раздел выше). Все 7
исправлены в этом же PR, отдельным commit `fix(sec-005): address
independent backfill review` поверх исходного HEAD
`b8e2def0736c74e4fdfe1947dd485a42dc00e4e4`.

### 1. Last-admin-гейт проверял не КАЖДУЮ существующую компанию

**Было**: гейт «есть ли хотя бы один admin» строился только по компаниям,
для которых нашлась хотя бы одна confirmed legacy-relation — компания без
единой legacy-связи (и без admin) молча проходила apply.
**Стало**: `buildPlan()` принимает новый обязательный параметр
`allCompanyIds: ReadonlySet<string>` (вычисляется в CLI как
`new Set(companies.map(c => c.docId))` из `readAllCompanies()`) и итерирует
именно его. Плюс: admin-статус компании считается ТОЛЬКО через
`isStrictlyValidActiveMembership(uid, data) && data.role === 'admin'` —
повреждённый документ с `role: 'admin'` больше не защищает apply.
Файлы: `scripts/lib/planner.ts`, `scripts/lib/firestoreReaders.ts`
(`computeExistingActiveAdmins`), `scripts/backfill-memberships.ts`.

### 2. `accept_existing` мог принять НЕ строго валидный membership

**Было**: классификация существующего membership была бинарной
(`exact_match` / `differs_or_invalid`) — `accept_existing` фактически мог
подтвердить документ с неизвестной ролью, `status !== 'active'`, чужим
`uid`, отсутствующими timestamps или лишними полями.
**Стало**: новая 4-значная классификация
`'not_found' | 'exact_match' | 'differs_but_valid' | 'invalid'`
(`scripts/lib/membershipValidation.ts`, новая экспортируемая
`isStrictlyValidActiveMembership()`). `accept_existing` резолвит ТОЛЬКО
`'differs_but_valid'`; `'invalid'` безусловно становится нерешённым
`existing_membership_conflict`, независимо от decision.

### 3. Rollback был уязвим к подмене source-report и TOCTOU-гонке

**Было**: rollback не проверял схему/mode/environment/projectId source
report и не защищал `get()`→`delete()` от изменения документа между чтением
и удалением.
**Стало**: новый чистый модуль `scripts/lib/rollbackValidation.ts` —
`validateSourceReportForRollback(raw, {environment, projectId})` — отвергает
(без единого удаления): не-объект, неверный `schemaVersion`, `mode !==
'apply'`, несовпадение environment/projectId, нарушение канонического пути
в `rollbackManifest`, дубликаты пар, записи без соответствия в
`createdPaths`/`plannedCreates` (включая ожидаемые role/status/timestamps).
Само удаление (`rollbackOneEntry` в `backfill-memberships.ts`) теперь
использует Firestore-precondition `ref.delete({ lastUpdateTime:
snap.updateTime })` — изменение документа между чтением и удалением
гарантированно приводит к отказу удаления, а не к race.

### 4. Observed checksum мог подставлять ожидаемые значения вместо прочитанных

**Было**: при отсутствии документа в read-back checksum мог быть посчитан
по ожидаемому (target) значению, маскируя частичный сбой записи.
**Стало**: новый чистый модуль `scripts/lib/observedState.ts` —
`computeObservedState(target, readBack)` — для каждой target-relation берёт
ТОЛЬКО фактически прочитанное; при отсутствии — `missing[]` +
sentinel-значение `'MISSING'` в checksum-входе (никогда не подставляет
target-значение); при расхождении — `differing[]`. Используется идентично
для apply (read-back после записи) и verify. Добавлена проверка exit-кода:
`mode === 'apply' && observedChecksum !== targetChecksum` → код 1.

### 5. Проверка безопасного пути отчёта выполнялась ПОСЛЕ начала Firestore I/O и не применялась к decisions/source-report

**Было**: `--report-path` проверялся отдельной inline-функцией уже после
`assertEnvironmentGuard`/`initFirestore`; `--decisions-file` и `--from-report`
вообще не проверялись на «вне репозитория».
**Стало**: новый общий модуль `scripts/lib/pathSafety.ts` —
`assertPathOutsideRepo(label, path, repoRoot)` — резолвит symlink-и через
`fs.realpathSync` (включая ещё не созданные конечные файлы), сравнивает
регистронезависимо на `win32`/`darwin`. Применяется КО ВСЕМ трём флагам
(`--report-path`, `--decisions-file`, `--from-report`) сразу после
`parseCliArgs()`, до `assertEnvironmentGuard`/`initFirestore`/любого I/O —
невалидный путь гарантированно даёт 0 записей.

### 6. Повреждённые legacy-источники молча пропускались

**Было**: пользователь без единой пригодной relation просто исчезал из
отчёта; malformed-записи в `companies[]` не отражались нигде; пара с ОДНОЙ
валидной И ОДНОЙ невалидной claim на одну и ту же роль тихо подтверждалась
через валидную claim.
**Стало**: `scripts/lib/legacyMapping.ts` теперь возвращает
`unknownUsers: {uid, reason: 'no_usable_relations'}[]` (пользователь без
единой пригодной relation) и `malformedClaims: {uid, reason:
'malformed_companies_entry'}[]` (не-объектные/без `companyId` записи в
`companies[]`, ранее — тихий `continue`). Новый `ConflictReason` —
`'mixed_role_validity'`: пара с валидной И невалидной role-claim теперь
безусловно становится конфликтом, а не auto-confirmed relation. `planner.ts`
дополнительно фильтрует `unknownUsers` — пользователь не считается unknown,
если для него уже есть строго валидный существующий membership где-либо.

### 7. `readAllExistingMemberships()` мог захватить чужие/вложенные `members`-документы

**Было**: чтение полагалось на `collectionGroup('members')` без проверки
формы полного пути — документ в любой вложенной `members`-подколлекции
(не строго `companies/{companyId}/members/{uid}`) мог повлиять на
planning/checksums/admin-гейт.
**Стало**: `firestoreReaders.ts` валидирует каждый путь: ровно 4 сегмента,
`segments[0] === 'companies'`, `segments[2] === 'members'`,
`uid === doc.id` — всё остальное отбрасывается до попадания в Map.

## Исправления по итогам ПОВТОРНОГО независимого аудита

Второй раунд независимого ревью вернул `REVIEW_RESULT: CHANGES REQUIRED` с
ещё 7 категориями блокирующих замечаний — на этот раз глубже: недостаточная
строгость `verify`, duck-typing Timestamp, `unknownUsers`/`malformedClaims`
как чисто информационные (не блокирующие) записи, недостаточная повторная
проверка `confirm_role`, неполнота `decisionsChecksum`, делимитерный
`relationKey`, и `computeObservedState`, сравнивавший только role/status.
Все 7 исправлены в этом же PR, отдельным commit `fix(sec-005): close second
independent review findings` поверх HEAD
`8ad991a6affebe52233c0bfd88b5f25d9df24143`.

### 1. `verify` мог дать ложный PASS через совпадение ПУСТЫХ checksums

**Было**: `verification.matchesTarget` вычислялся ТОЛЬКО как равенство
`observedChecksum === targetChecksum`. Компания с нерешённым конфликтом и
без единого запланированного/пропущенного relation давала ПУСТОЙ
`targetChecksum` (хеш `[]`) — и если ничего не было применено,
`observedChecksum` тоже был хешем `[]`. Два пустых хеша совпадают →
`matchesTarget: true`, хотя план ВООБЩЕ не был разрешён.
**Стало**: `matchesTarget` теперь требует ОДНОВРЕМЕННО (`scripts/backfill-memberships.ts`):
`plan.applyAllowed` (план полностью разрешён — включая новый блокирующий
статус `unknownUsers`/`malformedClaims`, см. фикс #3 ниже), `missing.length
=== 0`, `differing.length === 0` и `observedChecksum === targetChecksum`.
`differing` сам стал строгим по схеме (фикс #7) — повреждённый документ
никогда не проходит, даже если role/status текстуально совпадают.

### 2. Timestamp проверялся duck-typing, а не реальным классом

**Было**: `isTimestampLike()` в `membershipValidation.ts` принимал ЛЮБОЙ
объект с числовыми `seconds`/`nanoseconds`, либо ЛЮБОЙ объект с функцией
`toDate` — то есть обычный JSON-объект `{seconds, nanoseconds}` или
поддельный `{toDate: () => new Date()}` проходили как валидный Timestamp.
**Стало**: `isRealTimestamp()` — `value instanceof Timestamp` (реальный
класс `firebase-admin/firestore`). Импорт класса не требует
инициализированного Admin SDK app — используется как чистое значение
(`Timestamp.now()`), поэтому модуль остаётся тестируемым без эмулятора.
Все "валидные" fixtures в unit-тестах (`membershipValidation.test.ts`,
`planner.test.ts`, `observedState.test.ts`) переведены на реальный
`Timestamp.now()`; добавлены отдельные тесты, доказывающие, что plain-map
и поддельный `toDate` теперь `invalid`.

### 3. `unknownUsers`/`malformedClaims` были чисто информационными

**Было**: `PlanResult.unknownUsers`/`malformedClaims` попадали в отчёт, но
НИКАК не влияли на `applyAllowed` — apply/verify могли пройти, даже если
пользователь без единой usable-relation или повреждённая `companies[]`-запись
были обнаружены.
**Стало**: `planner.ts`'s `applyAllowed` теперь требует
`unknownUsers.length === 0 && malformedClaims.length === 0`. Добавлен новый
безопасный механизм явного подтверждения — **user-level decision**:
`Decision.companyId` стал опциональным (`scripts/lib/types.ts`); decision
без `companyId` обязан иметь `resolution: 'exclude'`
(`scripts/lib/decisions.ts` валидирует это условие) и адресует запись по
`uid` напрямую (нет `companyId`, который можно было бы использовать для
адресации — у `unknownUsers`/`malformedClaims` его никогда не было).
Никакого молчаливого игнорирования не осталось: запись остаётся блокирующей,
пока либо не появится явный user-level `exclude` decision, либо не будет
исправлен источник данных (после чего запись просто перестанет
экстрактироваться).

### 4. `confirm_role` не перепроверял существование company/user

**Было**: (a) `planner.ts` применял `confirm_role` decision, доверяя
`companyId`/`uid` конфликта/anomaly без повторной проверки, что они
СЕЙЧАС существуют; (b) `legacyMapping.ts`'s id-mismatch-ветка создавала
`user_id_mismatch` conflict для ЛЮБОГО companyId в claims — включая
несуществующие — что означало, что `confirm_role` decision мог "создать"
membership под отсутствующей компанией.
**Стало**: (a) `planner.ts` добавил `confirmRoleTargetExists()` — перед
применением ЛЮБОГО `confirm_role` decision (и для conflicts, и для owner
anomalies) проверяется `allCompanyIds.has(companyId) && allUserIds.has(uid)`
(новый параметр `allUserIds` добавлен в `BuildPlanParams`, вычисляется в
`backfill-memberships.ts` из `readAllUsers()`); при несовпадении decision
игнорируется, запись остаётся unresolved. (b) `legacyMapping.ts` теперь
проверяет существование company ПЕРЕД классификацией id-mismatch claim: при
отсутствующей компании это `missing_company` **orphan** (никогда
`user_id_mismatch` conflict) — а orphans, по уже существующему правилу
`planner.ts`, разрешаются ТОЛЬКО через `exclude`, никогда через
`confirm_role`. Дополнительно: id-mismatch документ без единой usable claim
теперь тоже попадает в `unknownUsers`, а не исчезает молча.

### 5. `decisionsChecksum` был недостаточно нормализован

**Было**: `computeDecisionsChecksum()` принимала слабо типизированный
параметр (`{companyId, uid, resolution}[]`) и сортировала по составному
строковому ключу из ТОЛЬКО этих трёх полей — при этом на практике полный
объект Decision всё же попадал в хеш (JS не обрезает лишние поля), но
контракт функции этого не гарантировал и не документировал, и сортировка не
была защищена от структурных изменений вызывающего кода.
**Стало**: `computeDecisionsChecksum(decisions: readonly Decision[])` явно
строит канонический объект из ВСЕХ 7 полей (`uid`, `companyId ?? null`,
`resolution`, `role ?? null`, `reason`, `reviewedBy`, `reviewedAt`) и
сортирует по канонической JSON-строке САМОГО объекта (полностью
детерминированно и порядко-независимо, без опоры на уникальность частичного
композитного ключа). Обновлено неверное/неполное утверждение в
`docs/migrations/MEMBERSHIP_BACKFILL.md` (раздел «Counts and checksum
contract») — теперь явно перечисляет все 7 полей.

### 6. `relationKey` был delimiter-based (риск коллизии)

**Было**: `relationKey()` строил ключ через `companyId + "::" + uid`
(с `String.fromCharCode` вместо литерала — защита от порчи ИСХОДНОГО
кода, но НЕ защита от коллизии, если сам `companyId`/`uid` содержит `::`
— т.е. `relationKey('co', 'a::u1') === relationKey('co::a', 'u1')`).
**Стало**: `relationKey()`/`splitRelationKey()` (`scripts/lib/types.ts`)
используют канонический JSON tuple: `JSON.stringify([companyId, uid])`.
JSON-кодирование строк экранирует ЛЮБОЙ символ, который мог бы сделать
границу массива неоднозначной — коллизия невозможна КОНСТРУКТИВНО, а не
только "маловероятна". `splitRelationKey()` строго валидирует форму
результата (ровно 2-элементный массив строк) и бросает исключение на
любом другом вводе. Новый файл `scripts/lib/types.test.ts` — 9 тестов,
включая явные случаи с `::`, пробелами, JSON-значимыми символами и Unicode
(эмодзи, кириллица, японский) в обоих идентификаторах одновременно.

### 7. `computeObservedState` сравнивал только role/status

**Было**: документ считался `differing` ТОЛЬКО если его `role` или `status`
текстуально отличались от target — документ с ПРАВИЛЬНЫМИ role/status, но
чужим `uid`, поддельными/отсутствующими timestamps или лишними полями
проходил как совпадающий.
**Стало**: `observedState.ts` теперь вызывает
`isStrictlyValidActiveMembership(uid, data)` для КАЖДОГО прочитанного
документа — при провале строгой схемы документ помечается `differing`
НЕЗАВИСИМО от совпадения role/status. Схема также участвует в самом
checksum: `LogicalRelation` (`checksum.ts`) получил новое поле
`schemaValid?: boolean` (target — всегда `true` по построению; observed —
явно вычисляется), поэтому повреждённый документ даёт другой
`observedChecksum`, даже если по чистому role/status он "совпал бы".

## Исправления по итогам ТРЕТЬЕГО независимого аудита

Третий раунд независимого ревью вернул `REVIEW_RESULT: CHANGES REQUIRED` с
4 категориями блокирующих замечаний — на этот раз про целостность rollback
manifest, честность учёта после успешной записи, целостность уже
существующих (не мигрируемых заново) membership-документов и коллизию
сортировки. Все 4 исправлены в этом же PR, отдельным commit `fix(sec-005):
close third independent review findings` поверх HEAD
`ba210bbfbf814bd0e5ea9c6c44e3b889a15cd1a3`.

### 1. Rollback manifest мог быть неполным без обнаружения

**Было**: `validateSourceReportForRollback()` проверял только направление
«каждая запись `rollbackManifest` имеет соответствие в `createdPaths`» —
обратное направление не проверялось вообще. Отчёт с ДВУМЯ созданными
документами, но только ОДНОЙ записью в `rollbackManifest`, проходил
валидацию и производил rollback, который тихо удалял только ОДИН из двух
реально созданных документов, при этом сообщая об успехе.
**Стало**: `scripts/lib/rollbackValidation.ts` теперь: (a) строго
валидирует КАЖДУЮ запись `createdPaths` независимо (канонический путь, нет
дублей внутри массива) — раньше эти записи вообще не проверялись
самостоятельно, только использовались как источник lookup; (b) требует
ТОЧНОГО равенства множеств пар `(companyId, uid)` между `rollbackManifest`
и `createdPaths` — несовпадение размеров или состава в ЛЮБУЮ сторону
отклоняет весь отчёт; (c) пустой `rollbackManifest` признаётся валидным
ТОЛЬКО когда `createdPaths` тоже пуст И `report.counts.created === 0` —
усечённый/подделанный manifest с пустым списком, но с непустыми
`createdPaths`/`counts.created`, отклоняется явно; (d) каждая созданная
пара по-прежнему должна соответствовать РОВНО ОДНОЙ записи
`plannedCreates` — неоднозначная (дублирующаяся) запись `plannedCreates`
для одной пары теперь тоже отклоняется, а не молча берётся первая
попавшаяся. Любое несовпадение отклоняет ВЕСЬ отчёт до какого-либо
Firestore I/O — ноль удалений.

### 2. Успешный create() мог быть потерян из-за отдельного чтения

**Было**: `ref.create()` и последующий `ref.get()` (для получения
`createTimeIso`/`updateTimeIso`) находились в ОДНОМ `try/catch` в
`backfill-memberships.ts` — успешный create с последующим неудачным get
записывался как write failure и полностью пропадал из
`createdPaths`/`rollbackManifest`, хотя документ реально существовал в
Firestore с этого момента.
**Стало**: новый модуль `scripts/lib/applyWrites.ts` —
`createPlannedRelations()` определяет успех ИСКЛЮЧИТЕЛЬНО по собственному
`WriteResult` вызова `ref.create()` (поле `writeTime`, которое ДЛЯ ТОЛЬКО
ЧТО СОЗДАННОГО документа одновременно является и `createTime`, и
`updateTime`) — второго чтения для подтверждения успеха больше нет вообще,
поэтому "успешный create + неудачное последующее чтение" структурно не
может произойти на уровне этой функции. Отдельно, `readBackObservedState()`
оборачивает пост-записевый read-back (`readAllExistingMemberships()`) в
собственный try/catch — если ЭТОТ вызов целиком падает (а не отдельный
документ), это раньше приводило к необработанному rejection, которое
обрывало `main()` ДО вызова `writeReport()` — теряя весь отчёт, включая уже
известные `createdPaths`. Теперь такой сбой возвращается как явный
`{ok: false, error}`, отчёт всё равно записывается (с новым полем
`readBackError: string | null`, честно отражающим случившееся), и exit
code остаётся ненулевым. Дополнительно: `assertReportPathWritable()`
(`scripts/lib/report.ts`) пробным byte-less write+delete проверяет
записываемость пути отчёта ДО получения credentials/Firestore I/O; сам
`writeReport()` теперь пишет во временный файл и делает atomic rename —
crash посреди записи не может оставить усечённый/повреждённый отчёт.

### 3. Существующие "осиротевшие" membership не проверялись на целостность родителей

**Было**: `isStrictlyValidActiveMembership()` проверял ТОЛЬКО собственную
схему документа (uid совпадает, известная роль, `status: 'active'`,
настоящие Timestamp, нет лишних полей) — но НЕ то, что родительская
компания и указанный пользователь реально существуют. Из-за этого: (a)
membership-документ под несуществующей компанией мог "засчитаться" как
покрытие для `unknownUsers` (подавляя честную запись о нерешённом
пользователе); (b) валидно выглядящий admin-membership, ссылающийся на
несуществующего `users/{uid}`, мог удовлетворить last-admin-гейт для
РЕАЛЬНОЙ компании.
**Стало**: `firestoreReaders.ts`'s `computeExistingActiveAdmins()` получил
новый обязательный параметр `allUserIds` — admin membership теперь
засчитывается ТОЛЬКО если `uid` есть среди реально существующих
пользователей. `planner.ts`'s Step 6 (подавление `unknownUsers`) теперь
дополнительно проверяет `allCompanyIds.has(companyId)` перед тем, как
membership может "покрыть" uid. Новый Step 7 в `planner.ts` сканирует ВСЕ
`existingMemberships`: документ, который строго валиден сам по себе, но
ссылается на несуществующую компанию ИЛИ несуществующего пользователя,
теперь безусловно всплывает как блокирующий `OrphanRecord` (`reason:
'missing_company'` или `'missing_user'`) — той же моделью подтверждения
(`exclude` decision), что и любой другой orphan. Важно: `exclude`
decision снимает только САМ ПУНКТ СПИСКА orphan — независимо
вычисляемые факты («этот membership не считается admin», «этот membership
не подавляет unknownUsers») читают `allCompanyIds`/`allUserIds` напрямую и
никогда не зависят от того, был ли orphan подтверждён decision-ом.
`apply` и `verify` возвращают ненулевой код, пока проблема не исправлена
в данных или явно не подтверждена decision-ом.

### 4. Коллизия сортировки `plannedCreates`/`skipped`

**Было**: финальная сортировка использовала
`(a.companyId + a.uid).localeCompare(b.companyId + b.uid)` — пары
`companyId='a',uid='bc'` и `companyId='ab',uid='c'` обе конкатенируются в
`"abc"`, из-за чего компаратор не может их различить (относительный
порядок между ними становится недетерминированным/зависящим от порядка
входных данных).
**Стало**: `planner.ts` использует уже существующий
`sortRelations()` (`checksum.ts`) — тот же корректный, коллизионно-
безопасный двухпольный компаратор (сначала `companyId`, затем `uid`),
который уже применялся для checksums.

**Было** (реализация третьего раунда, фикс #3): dangling existing
membership (документ, чья схема валидна сама по себе, но `companyId`/`uid`
не существует) добавлялся в `unresolvedOrphans` — тот же список, что и
legacy-source orphans, — и снимался ТЕМ ЖЕ `exclude` decision, что и
обычный orphan:
```ts
const decision = decisionByKey.get(key)
if (decision && decision.resolution === 'exclude') continue
```
Это позволяло pair-level `exclude` decision убрать dangling membership из
`unresolvedOrphans`, хотя документ физически оставался в Firestore. Если у
компании был ДРУГОЙ валидный admin (last-admin-гейт уже проходил
независимо от этого), единственным блокирующим сигналом для dangling
admin-membership оставался именно этот orphan-пункт — и после его
`exclude` `applyAllowed` мог стать `true`, а `verify` — вернуть success, с
повреждённым документом всё ещё на месте.

### Исправление

**Стало**: dangling existing memberships теперь репортятся в СОВЕРШЕННО
ОТДЕЛЬНОМ списке — `PlanResult.danglingMemberships` /
`report.danglingMemberships` (новый тип `DanglingMembershipRecord` /
`DanglingMembershipReason` = `'existing_membership_missing_company' |
'existing_membership_missing_user'`, `scripts/lib/types.ts`) — который
`decisionByKey`/`userLevelExcludedUids` НИКОГДА не консультируют ни при
каких условиях. Ни pair-level (`companyId`+`uid`), ни user-level (только
`uid`) `exclude` decision не может снять запись из этого списка. Единственный
способ снять блокировку — реально исправить данные (создать недостающую
компанию/пользователя или удалить сам dangling-документ) — тогда
СЛЕДУЮЩИЙ прогон просто не увидит эту запись, поскольку она вычисляется
заново каждый раз из фактического состояния Firestore.

`applyAllowed` теперь требует `danglingMemberships.length === 0`
безусловно. `counts.danglingMemberships` (новое поле `ReportCounts`)
честно отражает количество таких записей и учитывается в
`counts.unresolved`. `legacyMapping.ts`-orphans (`unresolvedOrphans`,
`OrphanRecord`/`OrphanReason`) остаются decision-resolvable ровно как
задокументировано — контракт для orphans, ссылающихся на ещё-не-мигрированные
legacy-claims (а не на физически существующие документы), не менялся.

### Что изменено в коде

`scripts/lib/firebaseAdmin.ts` — новая функция `assertCycleExecutionAllowed(environment)`,
намеренно отдельная от `assertEnvironmentGuard()` (та проверяет только
согласованность project ID, не авторизацию цикла на конкретное окружение).
`emulator` и `staging` теперь проходят этот gate; `production` **безусловно**
бросает `CycleExecutionError` — функция не читает
`--backup-reference`/`--rollback-reference`/`--ack-maintenance-readonly`
ни при каких условиях, ни один флаг не может изменить исход для production.

`scripts/backfill-memberships.ts`'s `main()` — заменён прежний
`if (environment !== 'emulator') return 4` на вызов
`assertCycleExecutionAllowed()` (тот же exit-код 4 при отказе, то же место
в потоке выполнения — после project-guard и production-флагов, до
`initFirestore()`/любого Firestore I/O).

### Почему production по-прежнему безопасен

`assertCycleExecutionAllowed('production')` бросает исключение
**безусловно**, независимо от того, переданы ли
`--backup-reference`/`--rollback-reference`/`--ack-maintenance-readonly`.
Существующая проверка этих флагов (строки выше в `main()`) осталась без
изменений и по-прежнему может первой вернуть код 3 при их отсутствии —
но даже при ВСЕХ трёх флагах, PRODUCTION_ACTION_APPROVED в этом цикле не
выдавался, поэтому `main()` в любом случае доходит до безусловного отказа
(код 4) раньше `initFirestore()`. Подтверждено emulator-тестом, реально
запускающим CLI-бинарник с этими тремя флагами против production — без
единого обращения к реальному Firestore (отказ происходит до
`initFirestore()`).

**`verify` должен получать ТОТ ЖЕ `--decisions-file`, что и `apply`.**
Decisions нигде не сохраняются в Firestore — это эфемерный входной файл;
если `verify` запущен без него (или с другим файлом), ранее разрешённый
через decision конфликт корректно вновь становится unresolved, и
`applyAllowed`/`matchesTarget` становятся `false` — это НЕ дефект
инструмента, а прямое следствие модели «decisions — внешний вход,
никогда не персистится». Шаг 5 выше воспроизводит это намеренно, как
часть репетиции, и служит живым регрессионным доказательством этого
поведения. Задокументировано также в `docs/migrations/MEMBERSHIP_BACKFILL.md`.

## Исправления production preflight по итогам независимого ревью

Независимый ревьюер рассмотрел production preflight (документационный
раунд, никогда не закоммиченный — доставлен только в чате) и вернул 9
категорий блокирующих замечаний: отсутствие `members` в backup, отсутствие
проверки counts/checksums для memberships после restore, ошибочное
именование Firestore `import` точным rollback, отсутствие описания
аварийного сценария утраты apply-report, запрещённый вариант «принять окно
риска» вместо реального maintenance/read-only механизма, неточные
mode-specific требования CLI, циклический `ROLLBACK_REFERENCE`,
отсутствие проверки backup/rollback/maintenance references перед
попаданием в отчёт, и требование сохранить production-gate безусловно
закрытым. Все 9 пунктов исправлены в этом же PR, отдельным commit
`fix(sec-005): correct production preflight safety design` поверх HEAD
`5f1e975771142c176189da8b75c65730ebe24976`. **Production не читался и не
изменялся ни разу в этом раунде** — вся работа выполнена против Firestore
Emulator и unit-тестов с fake Firestore stubs.

### 1. Collection group `members` отсутствовал в backup

**Было**: предложенная (ранее — только в чате, не закоммиченная) backup-
команда использовала `--collection-ids=users,companies,company_data` —
`companies/*/members/*` не попадал в export вообще, хотя это именно то,
что создаёт SEC-005 apply.
**Стало**: backup-команда исправлена на
`--collection-ids=users,companies,company_data,members` — Firestore
managed export матчит `--collection-ids` по ID коллекции ПО ВСЕЙ базе (та
же семантика, что и `collectionGroup()`), поэтому `members` в этом списке
корректно захватывает ВСЕ `companies/{companyId}/members/{uid}` документы
проектно-широко, независимо от глубины вложенности. Реализовано как
обязательная проверка, не только текст: `verifyBackupReference()`
(`scripts/lib/productionSafety.ts`) отклоняет манифест без
`firestore.membersCount: number` — backup без задокументированного числа
members-документов не может быть использован как `--backup-reference` для
production apply, независимо от того, что написано в runbook.

### 2. Отсутствовала проверка counts/checksums для memberships после restore

**Было**: раздел restore в `BACKUP_AND_RESTORE.md` (задача BASE-003, не
затронута этим раундом) не описывал проверку `members` после restore в
изолированный проект.
**Стало**: новый раздел «Restore verification — members collection group»
в `MEMBERSHIP_BACKFILL.md` (ниже) прямо предписывает, что restore-процедура
ДОЛЖНА подтвердить: (a) `gcloud firestore export`'s `outputUriPrefix`
включал `members` (видно в манифесте GCS, который `verifyBackupReference()`
теперь тоже требует через `membersCount`); (b) после `gcloud firestore
import` в изолированный restore-проект — количество документов
`companies/*/members/*` СОВПАДАЕТ с `firestore.membersCount` из manifest;
(c) это подтверждается тем же checksum-механизмом, что уже используется
самим backfill-инструментом (`sha256Hex` над каноническим JSON count-
объектом), а не только визуальным сравнением чисел. Это НЕ новая
процедура restore (BASE-003 остаётся владельцем механики export/import) —
это дополнительное обязательное поле в уже существующем manifest-контракте
BASE-003 §6.1, которое SEC-005's инструмент теперь программно проверяет.

### 3. Firestore `import` ошибочно назывался точным rollback

**Было**: черновой (не закоммиченный) preflight-текст описывал
`gcloud firestore import` как способ «откатить production» после
неудачного apply — не упоминая, что import — операция MERGE/OVERWRITE:
она НЕ удаляет документы, присутствующие в target, но отсутствующие в
export snapshot. Ровно это и создаёт SEC-005 apply — новые
`companies/*/members/*` документы, которых не было в pre-apply backup.
Полный import backup НЕ удалит их.
**Стало**: `MEMBERSHIP_BACKFILL.md`'s раздел «Production rollback» (ниже)
явно формулирует: «Firestore `import` — это MERGE/OVERWRITE, а не exact
rollback: он восстанавливает документы, присутствовавшие в backup, но НЕ
удаляет документы, созданные ПОСЛЕ backup и отсутствующие в нём. Для
отмены `apply` этого инструмента (создание новых `members` документов)
единственный надёжный способ — точечное удаление именно тех документов,
которые `apply` создал, что и делает `rollback-from-report`». Слово «exact
rollback» больше нигде не применяется к `import`.

### 4. `rollback-from-report` не был явно закреплён как основной rollback; аварийный сценарий утраты apply-report не описан

**Было**: не было явного заявления, какой механизм — основной, и что
делать, если apply-report физически утерян (единственный источник для
`rollback-from-report --from-report`).
**Стало**: `MEMBERSHIP_BACKFILL.md` теперь явно объявляет
`rollback-from-report` основным (и единственным штатным) rollback-
механизмом для production apply — он единственный делает ТОЧЕЧНОЕ удаление
именно созданных документов под Firestore precondition
(`lastUpdateTime`), в отличие от `import`. Новый раздел «Аварийный
сценарий: apply-report утерян» описывает деградированную процедуру на
случай физической утраты report-файла: (a) `apply-report` больше НЕ
восстановим — по дизайну он никогда не коммитится и не хранится в
Firestore; (b) единственный путь восстановления — полный `import`
pre-apply backup поверх production (принимая, что это MERGE, не удаление —
см. пункт 3 выше: любые НЕ созданные этим apply документы останутся
нетронутыми, что безопасно, потому что `import` не удаляет ничего лишнего,
он только перезаписывает существовавшие ранее версии); (c) после import —
ОБЯЗАТЕЛЬНЫЙ `--mode verify` прогон (без decisions-file, чтобы увидеть
сырое состояние) для подтверждения, что состояние `members` теперь
соответствует backup-манифесту по counts/checksum; (d) этот сценарий
явно помечен как «last resort», требующий отдельного явного
подтверждения владельца перед выполнением, и НЕ покрывается штатным
runbook flow.

### 5. Реальный maintenance/read-only механизм (вместо «принять окно риска»)

**Было**: черновой preflight предлагал «принять окно риска» (без
блокировки клиентских/Admin SDK writes во время apply) как единственный
практический вариант — прямо запрещённый вариант по заданию этого раунда.
**Стало**: спроектирован и реализован реальный, из двух независимых
уровней принудительного закрытия, механизм — потому что Firestore Rules
НИКОГДА не применяются к Admin SDK вызовам, и Rules-only решение было бы
недостаточным (именно на это указывало замечание про «Admin SDK writes из
createCompany»):
- **Клиентские Firestore writes** — `firestore.rules` получил
  `isMaintenanceModeActive()` (читает `system/maintenance` через
  `get()`/`exists()`, что НЕ подчиняется `allow read`-правилу самого
  `system/{doc}` — стандартное поведение Rules) и `&&
  !isMaintenanceModeActive()` добавлен к КАЖДОМУ client-write правилу
  (`users` self-create/update, `companies` create/update, `company_data`
  create/update — оба admin- и accountant-варианта). `system/maintenance`
  сам НИКОГДА не доступен клиенту на запись (falls through в
  deny-by-default catch-all в конце файла) — включить/выключить его может
  ТОЛЬКО Admin SDK, то есть оператор, выполняющий runbook.
- **Admin SDK writes из `createCompany`** — новая функция
  `requireNotInMaintenanceMode(db)` (`functions/src/lib/authz.ts`),
  вызывается ПЕРВЫМ шагом внутри `createCompany`'s handler (сразу после
  `requireAuth`, до любого чтения/записи) — читает тот же
  `system/maintenance` документ напрямую через Admin SDK (Rules к этому
  вызову вообще не применяются) и бросает `AppError('maintenance_mode')`
  (новый стабильный код, маппится на `failed-precondition`) при
  `enabled === true`.
- **Fail-closed на обоих уровнях**: ошибка чтения `system/maintenance`
  трактуется идентично `enabled === true` (отказ), никогда как «maintenance
  выключен» — ни в `isMaintenanceModeActive()` (Rules — `get()`/`exists()`
  внутри Rules не может «упасть» отдельно от общего отказа правила, так
  что отсутствие документа корректно даёт `false` без риска обхода), ни в
  `requireNotInMaintenanceMode()` (explicit try/catch → всегда бросает),
  ни в мигратора-side `assertMaintenanceModeActive()`
  (`scripts/lib/productionSafety.ts`).
- **Порядок**: `scripts/backfill-memberships.ts`'s production-apply-путь
  требует `await assertMaintenanceModeActive(db)` ПЕРЕД выполнением
  `createPlannedRelations()` — то есть maintenance должен быть включён (и
  верифицирован реальным чтением, не просто флагом `--ack-maintenance-
  readonly`, который дополнительно требуется как явное подтверждение
  оператора) до первой записи. Выключение — исключительно ручной шаг
  оператора runbook, выполняемый ПОСЛЕ `--mode verify` (задокументировано
  в новом разделе runbook ниже) — инструмент сам никогда не выключает
  maintenance mode, чтобы не создать окно между verify и выключением, в
  которое клиент мог бы записать до подтверждения корректности состояния.

### 6. Mode-specific требования CLI и точные команды

**Было**: черновой preflight использовал одну бланкетную проверку
(`backup-reference`/`rollback-reference`/`ack-maintenance` для ЛЮБОГО
non-verify режима production), не различая реальные требования каждого
режима, и не показывал точные будущие команды.
**Стало**: старая бланкетная проверка удалена. Новая таблица требований
(добавлена в `MEMBERSHIP_BACKFILL.md`, раздел «Production mode-specific
requirements», ниже) и код `scripts/backfill-memberships.ts` теперь точно
разделяют:

| Режим | `--backup-reference` | `--rollback-reference` | `--ack-maintenance-readonly` | Maintenance проверяется? |
|---|---|---|---|---|
| `dry-run` | нет | нет | нет | нет — dry-run ничего не пишет |
| `apply` | ДА, верифицируется (`verifyBackupReference`) | ДА, верифицируется против `targetChecksum` этого запуска (`verifyRollbackPlanReference`) | ДА, требуется | ДА (`assertMaintenanceModeActive`), fail-closed |
| `verify` | нет | нет | нет | нет — verify только читает |
| `rollback-from-report` | нет | нет | ДА, требуется | ДА (`assertMaintenanceModeActive`), fail-closed |

Точные команды для каждого режима (dry-run/apply/verify/rollback) заново
выписаны в `MEMBERSHIP_BACKFILL.md`, «Future production execution»
(обновлён, см. ниже).

### 7. Циклический `ROLLBACK_REFERENCE`

**Было**: черновой preflight требовал `ROLLBACK_REFERENCE` ДО apply, но
единственным содержательным значением для `rollback-from-report` является
путь к apply-report — который физически не существует до того, как apply
завершится. Циклическая зависимость.
**Стало**: двухфазная схема, реализованная в
`scripts/lib/productionSafety.ts`:
- **До apply**: `--rollback-reference` указывает на ПУТЬ К СУЩЕСТВУЮЩЕМУ
  `dry-run`-отчёту (`verifyRollbackPlanReference(path, targetChecksum)`) —
  требует `report.mode === 'dry-run'` (отклоняет apply-отчёт — закрывает
  саму возможность циклической ссылки на самого себя) И
  `report.targetChecksum === targetChecksum` ТЕКУЩЕГО запуска (доказывает,
  что оператор проверял ИМЕННО этот план изменений, а не устаревший или
  посторонний dry-run). Это НЕ описание будущего rollback — это
  доказательство, что оператор действительно рассмотрел dry-run перед тем,
  как запускать apply.
- **После apply**: инструмент отдельно вычисляет и печатает (никогда не
  встраивает В САМ отчёт — самоссылочный хеш недостижим: файл не может
  содержать хеш самого себя) SHA-256 только что записанного apply-report
  файла (`sha256OfFile`, вызывается ПОСЛЕ `writeReport()`). Именно это
  значение — `ROLLBACK_REFERENCE` для последующего вызова
  `rollback-from-report`, который валидирует `--from-report` тем же путём
  (существующий `validateSourceReportForRollback` из предыдущих раундов) —
  двухфазная схема закрывает circularity без нового постоянного хранилища.

### 8. Проверка backup/rollback/maintenance references + safe audit-часть отчёта

**Было**: `--backup-reference`/`--rollback-reference`/`--ack-maintenance-
readonly` были honour-system-флагами — CLI только проверял их присутствие
(не пустая строка), никогда не проверял их СОДЕРЖАНИЕ, и они не попадали
в отчёт вообще.
**Стало**: новый модуль `scripts/lib/productionSafety.ts` заменяет
honour-system на реальную верификацию: `verifyBackupReference()` читает и
парсит manifest-файл (реюз BASE-003 §6.1 схемы), проверяет
`productionProjectId`, `firestore.exportStatus === 'SUCCESS'`,
`firestore.membersCount` (пункт 1); `verifyRollbackPlanReference()`
проверяет dry-run report (пункт 7); `assertMaintenanceModeActive()`
проверяет реальное состояние `system/maintenance` в Firestore (пункт 5).
Новое поле отчёта `productionSafety: ProductionSafetyAudit`
(`scripts/lib/report.ts`) — ТОЛЬКО безопасные производные значения
(SHA-256 хеши файлов, timestamps, taskId) — НИКОГДА сырые пути файлов или
Firestore-идентификаторы — включено в `printSafeSummary()`, то есть
попадает в ту же safe-часть stdout-вывода, что и остальные агрегаты.
Отказ ЛЮБОЙ из трёх проверок останавливает apply/rollback ДО первой записи
(exit 3), и отражается в отчёте как `productionSafety: <пустые null-поля>`
— честный сигнал «проверка не пройдена», не скрытый.

### 9. Production-gate остаётся безусловно закрытым

`scripts/lib/firebaseAdmin.ts`'s `assertCycleExecutionAllowed()` **НЕ
изменён этим раундом** — по-прежнему безусловно бросает
`CycleExecutionError` для `environment === 'production'`, независимо от
`--backup-reference`/`--rollback-reference`/`--ack-maintenance-readonly`
или любых других флагов. Все изменения этого раунда (maintenance mode,
`productionSafety`-проверки, исправленная документация) готовят почву на
момент, когда production БУДЕТ явно разрешён отдельным `PRODUCTION_ACTION_
APPROVED` грантом в будущем цикле — они не открывают и не ослабляют
существующий безусловный gate. Подтверждено: `git diff origin/main...HEAD
-- scripts/lib/firebaseAdmin.ts` пуст.

## Исправления production preflight по итогам финального независимого ревью

Повторный независимый ревьюер рассмотрел раунд «Исправления production
preflight по итогам независимого ревью» (раздел выше) и вернул ещё 9
категорий блокирующих замечаний — более глубоких, чем в предыдущем
раунде: реальный порядок runbook не гарантировал включение maintenance ДО
backup; `createCompany` был уязвим к TOCTOU-гонке между начальной
проверкой maintenance и commit собственной транзакции; backup manifest
schema была недостаточно строгой; pre-apply dry-run reference принимал
почти пустой поддельный JSON; `--backup-reference`/`--rollback-reference`
не проходили через общий path-safety guard; `rollback-from-report` не
проверял целостность source-файла перед удалением; аварийный сценарий
утраты apply-report по-прежнему опирался на blind `import`. Все 9
исправлены в этом же PR, отдельным commit `fix(sec-005): close final
production preflight review findings` поверх HEAD `d0673640f56d5a1df102f4ab0e16ae28d0b361ef`.
**Production не читался и не изменялся ни разу в этом раунде** — вся
верификация против Firestore Emulator и unit fake-Firestore stubs.

### 1. Порядок runbook не гарантировал maintenance ДО backup

**Было**: «Future production execution» перечислял шаги как backup →
dry-run → enable maintenance → apply → verify → disable — maintenance
включался ПОСЛЕ backup, то есть backup мог быть снят при ещё активных
клиентских записях.
**Стало**: порядок переставлен на guards (отдельный будущий deploy
Rules/Functions) → создать `system/maintenance` в состоянии disabled →
ВКЛЮЧИТЬ maintenance → backup → dry-run/review → apply → verify →
выключить maintenance (`docs/migrations/MEMBERSHIP_BACKFILL.md`, раздел
«Future production execution», Steps 1–8). Порядок не только
задокументирован, но и программно обеспечен: `verifyBackupReference()`
теперь требует `manifest.createdAtUtc >= system/maintenance.enabledAt`
(читается ЖИВЫМ Firestore-запросом при `apply`, до проверки backup) — не
просто рекомендация в тексте.

### 2. TOCTOU-гонка в `createCompany` между проверкой maintenance и commit

**Было**: `requireNotInMaintenanceMode(db)` вызывался ОДНИМ обычным
(не-транзакционным) чтением сразу после `requireAuth`, ДО начала
`runBootstrapIdempotent`'s транзакции. Между этим чтением и фактическим
commit'ом транзакции (создающей company/membership/company_data/user)
проходило время (adminAuth.getUser(), несколько чтений внутри самой
транзакции) — оператор, включивший maintenance mode ровно в этот
промежуток, не мог остановить уже начавшуюся транзакцию.
**Стало**: `requireNotInMaintenanceMode(db, txn)`
(`functions/src/lib/authz.ts`) получил опциональный параметр `txn` —
внутри `createCompany`'s `run: async (txn) => {...}` вызывается ПЕРВЫМ
statement'ом (`functions/src/index.ts`), читая `system/maintenance` через
`txn.get()`. Это делает документ частью READ SET транзакции — если
`system/maintenance` изменится ЛЮБОЙ другой завершённой записью между
этим чтением и попыткой commit, Firestore автоматически ретраит ВСЮ
функцию транзакции (включая повторное выполнение этой же проверки) вместо
того, чтобы позволить commit со устаревшим прочитанным значением — тот же
паттерн, что уже использует `assertNotLastAdmin()` в этом же файле.
Подтверждено реальным emulator race-тестом
(`functions/test/emulator/createCompany.test.ts`, «closes the
maintenance-mode TOCTOU race»): `callCreateCompany()` запускается БЕЗ
ожидания, конкурентно с 8 прямыми `setMaintenanceMode(true)` записями —
create отклоняется с `maintenance_mode`, ноль компаний создано.
Стабильно воспроизведено в 2 независимых прогонах `test:emulator`.

### 3. Backup manifest schema была недостаточно строгой

**Было**: `verifyBackupReference()` проверял только
`productionProjectId`, `firestore.exportStatus === 'SUCCESS'`,
`firestore.membersCount` (наличие) и `createdAtUtc` (наличие строки) —
без проверки формата timestamp, без требования export operation ID, без
проверки, что counts — целые неотрицательные числа, без требования
restore-верификации, без проверки свежести/порядка относительно
maintenance mode.
**Стало**: `verifyBackupReference()` (`scripts/lib/productionSafety.ts`)
теперь требует: `firestore.exportOperationId` (непустая строка);
`firestore.collectionIds` содержит `"members"` ИЛИ `firestore.scope ===
'full'`; `membersCount`/`companiesCount`/`usersCount`/
`companyDataDocsCount` — целые неотрицательные числа
(`Number.isInteger(v) && v >= 0`); `restore.verificationResult ===
'PASS'` с `restore.membersCount === firestore.membersCount` и непустым
`restore.membersChecksum` (item 2 предыдущего раунда теперь реально
проверяется, а не только документирован); валидные ISO-timestamps
(`createdAtUtc`, `restore.verifiedAtUtc`); `createdAtUtc >=
maintenanceEnabledAtIso` (передаётся вызывающим кодом из РЕЗУЛЬТАТА
`assertMaintenanceModeActive()`, вызванного ПЕРВЫМ в apply-потоке); и
`now - createdAtUtc <= MAX_BACKUP_AGE_MS` (24 часа, новая экспортируемая
константа). `assertMaintenanceModeActive()` сам теперь ТРЕБУЕТ реального
`enabledAt` Timestamp — без него бросает `ProductionSafetyError`, потому
что freshness-проверка backup не может быть доказана без этого якоря.

### 4. Pre-apply dry-run reference принимал почти пустой поддельный JSON

**Было**: `verifyRollbackPlanReference()` проверял только `mode ===
'dry-run'` и совпадение `targetChecksum` — файл вида `{mode: 'dry-run',
targetChecksum: '...'}` без единого другого поля проходил валидацию.
**Стало**: новая общая функция `verifyStrictDryRunReport()`
(`scripts/lib/productionSafety.ts`) проверяет: `schemaVersion ===
REPORT_SCHEMA_VERSION`; `mode === 'dry-run'`; `environment ===
'production'`; `projectId` совпадает с `--project`; непустой
`sourceGitSha`; `sourceChecksum`/`decisionsChecksum`/`targetChecksum` —
каждый валидный 64-символьный hex SHA-256; `counts.unresolved === 0`
(план должен быть полностью разрешён); и структуру `plannedCreates`
(каждая запись — companyId/uid/role/status). `verifyRollbackPlanReference()`
делегирует эти проверки и добавляет сверку `targetChecksum` с текущим
запуском. Та же функция переиспользована для нового режима
`rollback-from-plan` (пункт 7 ниже) — единый контракт «это настоящий,
полностью разрешённый dry-run report» для обоих потребителей.

### 5. `--backup-reference`/`--rollback-reference` не проходили path-safety guard

**Было**: `main()`'s единый блок `assertPathOutsideRepo` покрывал
`--report-path`/`--decisions-file`/`--from-report`, но НЕ
`--backup-reference`/`--rollback-reference` — эти два флага шли прямиком в
`readFileSync()` внутри `productionSafety.ts`, минуя проверку «путь вне
репозитория, до credential acquisition/I/O».
**Стало**: оба флага добавлены в тот же начальный блок
`assertPathOutsideRepo` в `main()` (`scripts/backfill-memberships.ts`), до
`assertEnvironmentGuard`/`initFirestore`/любого I/O — тот же контракт, что
уже применялся к трём остальным path-флагам.

### 6. `rollback-from-report` не проверял целостность `--from-report`

**Было**: `rollback-from-report` читал и парсил `--from-report` без
какой-либо проверки, что содержимое файла — именно то, что оператор
записал как ROLLBACK_REFERENCE после `apply`; структурная валидация
(`validateSourceReportForRollback`) ловила логические несоответствия, но
не подмену/порчу файла на уровне байтов.
**Стало**: новый обязательный флаг `--expected-report-sha256` (проверка
формата — 64-символьный hex — на уровне `parseCliArgs`). В `runRollback()`
файл сначала читается как raw text, вычисляется `sha256Hex()` и
сравнивается с `--expected-report-sha256` — ДО `JSON.parse`, до
структурной валидации, до любого Firestore I/O. Несовпадение отклоняет
rollback (код 3) с нулём удалений.

### 7. Аварийный сценарий утраты apply-report опирался на blind `import`

**Было**: раздел «Emergency scenario: apply-report lost» (предыдущий
раунд) предлагал полный `gcloud firestore import` pre-apply backup как
запасной вариант — что противоречит собственному пункту 3 задания этого
раунда («import не удаляет документы, отсутствующие в backup») и не
восстанавливает гарантию «удалены только документы, созданные ИМЕННО этой
миграцией».
**Стало**: новый режим `--mode rollback-from-plan --from-plan
<dry-run-report>` (`runRollbackFromPlan()`,
`scripts/backfill-memberships.ts`). Реконструирует кандидатов из
`plannedCreates` ПРОВЕРЕННОГО (через `verifyStrictDryRunReport()`)
dry-run report; для каждого кандидата — реальное чтение живого документа;
удаление ТОЛЬКО если документ существует, ТОЧНО совпадает по
uid/role/status с планом, проходит строгую schema-валидацию
(`isStrictlyValidActiveMembership`), и под тем же
`lastUpdateTime`-precondition, что и `rollback-from-report`. Несовпадение
— отказ (`refused[]`), не удаление наугад. Требует отдельного,
дополнительного `--ack-emergency-reconstruction` (сверх
`--ack-maintenance-readonly`) — явное подтверждение, что это
деградированный, слабее по доказательности путь. Если и dry-run report
утерян — документирован честный `BLOCKED — требуется действие владельца`
(ручное восстановление), без единого автоматизированного «удали то, что
кажется подходящим».

### 8. Operator script для maintenance был лишь иллюстративным

**Было**: раздел «Maintenance/read-only mode» предыдущего раунда содержал

## Исправления SEC-005 по итогам второго прохода финального независимого ревью

Второй проход финального независимого ревью нашёл ещё 5 категорий
блокирующих замечаний в предыдущем раунде («Исправления production
preflight по итогам финального независимого ревью» выше). Все 5
исправлены в этом же PR, отдельным commit `fix(sec-005): close second
pass of final production preflight review` поверх HEAD
`3bfb88e4e419efc9ad3e7506a9f5cdbcf72fc254`. **Production не читался и не
изменялся ни разу в этом раунде** — вся верификация против Firestore
Emulator и unit fake-Firestore stubs.

### 1. `rollback-from-plan` не имел integrity-check на `--from-plan`

**Было**: `--mode rollback-from-report` требовал `--expected-report-sha256`
(предыдущий раунд), но `--mode rollback-from-plan` — структурно идентичная
по риску операция (тоже читает внешний JSON-файл и на его основе удаляет
Firestore-документы) — не имела эквивалентной проверки: подменённый или
повреждённый `--from-plan` парсился и обрабатывался без какой-либо
проверки целостности байтов.
**Стало**: новый обязательный флаг `--expected-plan-sha256` (валидация
формата — 64-символьный hex — на уровне `parseCliArgs`). В
`runRollbackFromPlan()` файл сначала читается как raw text, вычисляется
`sha256Hex()` и сравнивается с `--expected-plan-sha256` — ДО `JSON.parse`,
ДО структурной валидации (`validateStrictDryRunReportContent`), ДО любого
Firestore read/delete. Несовпадение отклоняет операцию (код 3) с нулём
Firestore-чтений и нулём удалений — подтверждено новым emulator-тестом
(см. ниже), реконструирующим ПОЛНОФОРМАТНЫЙ dry-run report с реально
существующим (совпадающим с планом) live-membership: при неверном hash
документ остаётся байт-в-байт неизменным, а `report.emergencyReconstruction`
остаётся `null` (это поле заполняется ТОЛЬКО после завершения цикла
чтения кандидатов — его отсутствие доказывает, что цикл вообще не
начинался).

Заодно рефакторинг: `scripts/lib/productionSafety.ts`'s
`verifyStrictDryRunReport()` (принимала путь, сама читала файл) разделена
на чистый `validateStrictDryRunReportContent(raw, ...)` (без I/O) +
`verifyStrictDryRunReport(path, ...)` (тонкая обёртка с чтением файла) —
`runRollbackFromPlan()` теперь читает файл РОВНО ОДИН раз (для hash-check),
затем передаёт уже прочитанный raw text в `validateStrictDryRunReportContent`
напрямую — без повторного чтения и без TOCTOU-разрыва между hash-check и
валидацией содержимого.

### 2. `--rollback-reference` сверялся только по `targetChecksum`

**Было**: `verifyRollbackPlanReference()` проверял структуру dry-run
report'а (`verifyStrictDryRunReport`) и сверял ТОЛЬКО `targetChecksum` с
текущим прогоном — dry-run, построенный на другом коммите, с другими
legacy-данными или с ДРУГИМ decisions-файлом (но случайно давший тот же
итоговый `targetChecksum`), формально проходил проверку. Кроме того,
`sourceGitSha === 'unknown'` (git-команда не сработала) нигде не
проверялся отдельно для production.
**Стало**: `verifyRollbackPlanReference(path, current: {sourceGitSha,
sourceChecksum, decisionsChecksum, targetChecksum}, expectedProjectId)` —
новая сигнатура требует ТОЧНОГО совпадения ВСЕХ ЧЕТЫРЁХ полей между
`--rollback-reference` и текущим прогоном apply. Отдельная явная проверка:
`current.sourceGitSha === 'unknown'` отклоняется НЕМЕДЛЕННО, до чтения
файла `--rollback-reference` вообще. Та же проверка `sourceGitSha !==
'unknown'` добавлена и в `validateStrictDryRunReportContent()` — но ТОЛЬКО
когда `expectedEnvironment === 'production'` (dry-run отчёты для
emulator/staging по-прежнему допускают `unknown`, поскольку туда часто
запускаются в средах без `.git`, например CI-контейнерах). Дополнительно:
`plannedCreates` теперь проверяется на отсутствие дублирующихся пар
`(companyId, uid)` — дубликат отклоняет весь report.

### 3. Backup manifest не требовал source members checksum

**Было**: `verifyBackupReference()` требовал `restore.membersChecksum` как
непустую строку, но НИКОГДА не сравнивал её ни с чем — поле существовало
только "для галочки", подделанный или произвольный checksum проходил
валидацию так же, как правильный.
**Стало**: манифест теперь требует НОВОЕ обязательное поле
`firestore.membersChecksum` (SOURCE/production checksum, вычисленный на
момент export, валидный 64-символьный hex) — `restore.membersChecksum`
теперь тоже строго валидируется как 64-hex И должен ТОЧНО РАВНЯТЬСЯ
`firestore.membersChecksum`. Несовпадение (даже при обоих полях
формально валидных) отклоняет backup-reference.

### 4. Runbook Step 5 мог произвести rollback-reference с несовместимым decisionsChecksum

**Было**: Step 5 (предыдущий раунд) описывал ОДИН dry-run БЕЗ
`--decisions-file`, чей report становился `--rollback-reference` для
apply, который САМ использовал реальный `--decisions-file`. Поскольку
`decisionsChecksum` вычисляется от содержимого decisions-файла (пустой
массив даёт один checksum, реальные decisions — другой), эта пара
НИКОГДА не могла пройти проверку item 2 — runbook описывал
самопротиворечивую последовательность команд.
**Стало**: Step 5 переписан на три подшага: 5a discovery dry-run (без
decisions, чтобы найти конфликты) → подготовка decisions-файла → 5b
RESOLVED dry-run (С ТЕМ ЖЕ `--decisions-file`, что будет использован в
apply) — именно ЕГО report становится `--rollback-reference` → 5c
сохранить SHA-256 этого report'а (нужен позже как `--expected-plan-sha256`
для аварийного `rollback-from-plan`). Step 6 (apply) явно указывает
использовать ТОТ ЖЕ `--decisions-file`, что и Step 5b, и report ИМЕННО
Step 5b (не Step 5a) как `--rollback-reference`. Аварийная
`rollback-from-plan` команда (раздел «Emergency scenario: apply-report
lost») обновлена: добавлен `--expected-plan-sha256 <resolved-dry-run-sha256,
saved in Step 5c>`.

### 5. Emulator/staging rollback-примеры не соответствовали реальному CLI

**Было**: `apply` печатал строку "Apply report SHA-256..." ТОЛЬКО для
`environment === 'production'` — хотя `--expected-report-sha256` уже был
безусловно обязателен для ЛЮБОГО `rollback-from-report` (предыдущий
раунд). Emulator walkthrough показывал команду `rollback-from-report` БЕЗ
`--expected-report-sha256` вообще — то есть документированная команда не
соответствовала фактическому CLI и не смогла бы выполниться.
**Стало**: условие печати SHA изменено с `environment === 'production' &&
createdPaths.length > 0` на `createdPaths.length > 0` (для ЛЮБОГО
environment). `docs/migrations/MEMBERSHIP_BACKFILL.md`'s «Emulator
walkthrough» переписан: apply-шаг явно комментирует, что печатается SHA
для любого окружения, rollback-шаг требует `--expected-report-sha256`, и
добавлена запасная инструкция (`sha256sum`/`Get-FileHash`) на случай,
если оператор не сохранил напечатанную строку. `verify`-пример также
получил `--decisions-file` (соответствует операционному правилу «verify
должен получать тот же decisions-file, что и apply», задокументированному
ранее, но не отражённому в этом конкретном примере).

исправлены в этом же PR, отдельным commit `fix(sec-005): close third pass

### 1. `rollback-from-plan` проверял maintenance mode ДО integrity-check

**Было**: `runRollbackFromPlan()` в `scripts/backfill-memberships.ts`
сначала (для production) вызывал `assertMaintenanceModeActive(db)` —
РЕАЛЬНОЕ Firestore-чтение — и только ПОТОМ читал `--from-plan`, проверял
`--expected-plan-sha256` и валидировал структуру. То есть подменённый или
неверный `--from-plan` в production-shaped flow ВСЁ РАВНО вызывал одно
реальное Firestore-чтение до отказа — противоположный порядок тому, что

**Стало**: логика вынесена в новый модуль
`scripts/lib/emergencyReconstruction.ts` —
`runEmergencyReconstruction(params)` — с явным, задокументированным
порядком: (1) чтение raw `--from-plan` (файловый I/O, не Firestore); (2)
сравнение `sha256Hex()` с `--expected-plan-sha256`; (3) структурная
валидация (`validateStrictDryRunReportContent`); (4) ТОЛЬКО ПОСЛЕ пунктов
1-3 — если `environment === 'production'` — проверка
`--ack-maintenance-readonly` и вызов `assertMaintenanceModeActive(db)`;
(5) цикл чтения/удаления кандидатов. `scripts/backfill-memberships.ts`'s
`runRollbackFromPlan()` теперь — тонкая CLI-обёртка, вызывающая эту
функцию и транслирующая результат в exit-код/отчёт.

Модуль вынесен ИМЕННО для тестируемости: `backfill-memberships.ts` нельзя
импортировать в unit-тесте — его module-level `main().then(...)` вызов
выполнил бы весь CLI как побочный эффект загрузки файла. Новый
`scripts/lib/emergencyReconstruction.test.ts` использует fake Firestore

production-shaped flow» (валидный `enabled: true` maintenance-документ
доступен, но подставлен заведомо неверный `--expected-plan-sha256`)
напрямую подтверждает: `getCount() === 0`, `deleteCount() === 0`, код

структуре, но НЕ активном maintenance — РОВНО ОДНО чтение (сама проверка
maintenance), ноль чтений кандидатов, ноль удалений — доказывая, что
порядок именно «валидация → потом (и только потом) один осмысленный
Firestore-запрос», а не «Firestore вообще никогда не трогается».

### 2. Runbook разрешал пересчитывать expected plan SHA из уцелевшего файла

**Было**: раздел «Emergency scenario: apply-report lost» (предыдущий
раунд) содержал: «If Step 5c's SHA-256 wasn't saved at the time,
recompute it the same way». Это делает всю проверку `--expected-plan-sha256`
бессмысленной: хеш, вычисленный из ТОГО ЖЕ файла, который он должен
проверять, всегда «совпадёт» с этим файлом — независимо от того, был ли
файл подменён, повреждён или атакован. Единственная ценность независимо
сохранённого hash — в том, что он записан ДО инцидента, когда
целостность файла ещё не была под вопросом.
**Стало**: Step 5c (`docs/migrations/MEMBERSHIP_BACKFILL.md`) теперь явно
требует хранить hash ОТДЕЛЬНО от plan-файла (не «ещё одна копия рядом на
том же диске») и ДО запуска apply. Формулировка «recompute» полностью
удалена. Новый подраздел «If the independently-saved hash is lost» в
«Emergency scenario: apply-report lost»: если независимо сохранённый
hash утрачен — даже если сам plan-файл цел — статус безусловно `BLOCKED
— требуется действие владельца`, тот же путь, что и при утрате самого
plan-файла (описано ниже, в «If no dry-run report survives either»).

### 3. Регистрозависимое сравнение SHA-256

**Было**: `SHA256_HEX_PATTERN = /^[0-9a-f]{64}$/i` (регистронезависимая
проверка ФОРМАТА) использовался для валидации `--expected-report-sha256`/
`--expected-plan-sha256`, но фактическое СРАВНЕНИЕ в
`backfill-memberships.ts` (`actualReportSha256 !== opts.expectedReportSha256`)
было строгим `!==` — регистрозависимым. `sha256Hex()` (Node crypto) всегда
возвращает lowercase hex, но PowerShell's `Get-FileHash -Algorithm SHA256`
(рекомендованный в документации команда для операторов) по умолчанию
выводит UPPERCASE hex. Оператор, честно скопировавший вывод
`Get-FileHash`, получил бы ложный отказ «hash mismatch» на полностью
корректном файле.
**Стало**: `scripts/lib/cli.ts`'s `parseCliArgs()` нормализует ОБА флага
(`--expected-report-sha256`, `--expected-plan-sha256`) в lowercase СРАЗУ
при парсинге (`.toLowerCase()`), в единственной точке входа — все
последующие сравнения остаются простым регистрочувствительным `===`, не
требуя от каждого вызывающего кода помнить о регистронезависимости.
Добавлены тесты с UPPERCASE и MIXED-case входом для обоих флагов.

### 4. Backup manifest не проверял порядок `restore.verifiedAtUtc`

**Было**: `restore.verifiedAtUtc` проверялся только на формат (валидный
timestamp), но не на логическую согласованность с остальными
timestamp'ами манифеста — манифест с `verifiedAtUtc` РАНЬШЕ, чем
`createdAtUtc` (проверка «утверждает», что backup был проверен ДО того,
как он был создан), или `verifiedAtUtc` В БУДУЩЕМ относительно текущего
момента, проходил валидацию.
**Стало**: `verifyBackupReference()` (`scripts/lib/productionSafety.ts`)
теперь требует `Date.parse(createdAtUtc) <= Date.parse(restore.verifiedAtUtc)
<= Date.parse(nowIso)`. Оба нарушения (restore до backup; restore в
будущем) отклоняются с конкретным сообщением об ошибке. Добавлены тесты
на оба случая, плюс граничные случаи (verifiedAtUtc точно равен
createdAtUtc / точно равен nowIso — оба должны проходить).

### 5. `ProductionSafetyAudit.backupReference` не содержал `membersChecksum`

**Было**: `BackupReference` (возвращаемое значение `verifyBackupReference()`)
уже содержал проверенный `membersChecksum` (добавлено во втором проходе,

`backupRef.membersChecksum` в объект `productionSafety`. Присутствие
этого поля в отчёте — само по себе доказательство, что source/restore
checksum сравнение прошло успешно (поле заполняется ТОЛЬКО после
успешного `verifyBackupReference()`). Новый `describe`-блок в
`report.test.ts`: round-trip через `writeReport()`/чтение файла, и
присутствие в `printSafeSummary()`'s stdout-выводе.

### Важно: backup этого preflight — верификационный, НЕ для apply

Даже после того как Phase 2 (создание и верификация backup) будет
выполнен, полученный backup **нельзя** будет использовать как
`--backup-reference` для будущего `apply` — по двум независимым причинам:

1. **Свежесть.** `verifyBackupReference()` отклоняет backup старше
   `MAX_BACKUP_AGE_MS` (24 часа, `scripts/lib/productionSafety.ts`)
   относительно момента `apply`. `apply` потребует отдельного,
   собственного `PRODUCTION_ACTION_APPROVED` раунда в будущем — почти
   наверняка этот backup к тому моменту уже устареет.
2. **Порядок относительно maintenance mode.** `verifyBackupReference()`
   также требует `createdAtUtc >= system/maintenance.enabledAt` (см.
   «Backup reference verification» в `docs/migrations/MEMBERSHIP_BACKFILL.md`).
   В этом раунде maintenance mode НЕ включался (см. выше) — то есть даже
   без учёта свежести, у этого backup нет валидного `enabledAt`, которому
   он мог бы соответствовать.

Значит: **`apply` в будущем потребует НОВОГО backup**, созданного ПОСЛЕ
того, как maintenance mode будет отдельно, явно разрешён и включён —
именно в этом порядке (guards → создать `system/maintenance` disabled →
включить maintenance → backup → dry-run/review → apply), как и описывает
раздел «Future production execution» в
`docs/migrations/MEMBERSHIP_BACKFILL.md`. Backup, создаваемый в РАМКАХ
ЭТОГО preflight-раунда, служит ТОЛЬКО для проверки, что весь механизм
export → import → checksum-сверка → manifest реально работает
end-to-end против реальных production-данных — не как заготовка для
будущего apply.
