## Почему изменения входят в текущий пункт

Все перечисленные файлы реализуют исключительно
`inviteMember({ companyId, email, role })` и его прямые зависимости
(генерация/хеширование токена, response-схема, один новый код ошибки,
тестовая инфраструктура для этого callable). `vitest.config.mts` — не
логика продукта, а исправление тестовой инфраструктуры, ставшее
необходимым строго из-за добавления второго emulator-тестового файла в
рамках этой же задачи (без него нельзя было бы честно подтвердить «полный
emulator suite дважды зелёный», что требуется чек-листом). Ничего из
`listInvitations`/`cancelInvite`/`resendInvite`/`previewInvite`/
`acceptInvite`, UI, отправки писем, создания Auth-пользователя, Rules для
`members`, деплоя — не реализовано и не тронуто (согласно явному
ограничению scope).

## Round 2: исправления по независимому аудиту

`SEC_006_STAGE2_CHANGES_REQUIRED` (round 1) признал сам callable корректным
(авторизация, транзакционный lock, токен вне retry-цикла, SHA-256, атомарные
invitation/lock/audit, fail-closed на повреждённых данных), но указал 5
пробелов в доказательной части. Исправляющий коммит: см. `git log` этой
ветки после коммита `17d2570` (SEC-006 Stage 2: add inviteMember server
callable).

1. **`expiresAtUtc` — только непустая строка, а не строгий UTC ISO.**
   Исправлено: `InviteMemberResponseSchema.expiresAtUtc` теперь
   `z.iso.datetime()` (Zod v4) — принимает ровно формат
   `Date.prototype.toISOString()` (миллисекунды, суффикс `Z`), отклоняет
   любой другой offset/формат. Добавлены unit-тесты (принимает реальный
   `toISOString()`; отклоняет `+02:00`, дату без времени, произвольную
   строку). В emulator happy-path добавлен точный assert:
   `Date.parse(response.expiresAtUtc) === (stored.expiresAt as Timestamp).toMillis()`.
2. **Happy-path не читал audit event.** Исправлено: добавлен хелпер
   `getAuditEvents(companyId)` в `functions/test/emulator/helpers.ts`;
   happy-path тест теперь читает реальный audit-документ и проверяет точный
   набор полей (`{action, actorUid, createdAt, targetUid}`), `action ===
   'member_invited'`, `targetUid === null`, и явное отсутствие
   `token`/`tokenHash`/`email`/`role` — включая сериализованную проверку,
   что email нигде в audit-событии не встречается.
3. **Негативные тесты считали только invitations.** Исправлено: добавлен
   общий хелпер `expectNoWritesAtAllFor(companyId, email)` (0 invitations, 0
   lock, 0 audit events), применён к unauthenticated, unverified, non-admin
   (viewer+accountant), cross-company, malformed-payload и maintenance
   тестам. К трём corrupted-state тестам (сценарий 16) также добавлен
   явный `countAuditEvents(...) === 0`.
4. **«Forced retry» тест не доказывал факт retry.** Исправлено правильным
   способом, а не патчем существующего теста: `inviteMember`
   рефакторен — транзакционное тело вынесено в отдельный, независимо
   unit-тестируемый модуль `functions/src/lib/inviteMemberTransaction.ts`
   (`runInviteMemberTransaction`), который НЕ импортирует
   `generateRawInvitationToken`/`hashInvitationToken`/`node:crypto` вообще —
   структурно не может их вызвать. `performInviteMember` (новый
   экспорт в `functions/src/index.ts`) принимает инъецируемый
   `runTransactionImpl` (по умолчанию — реальный `db.runTransaction`).
   Новый `functions/test/unit/inviteMemberTransaction.test.ts`:
   - структурная проверка (`import`-строки модуля не содержат имён

   Старый emulator-тест (сценарий 17) сохранён как дополнительная
   эмпирическая проверка, его комментарий переписан честно: он не

## Security review

- Авторизация полностью fail-closed: любая ошибка чтения/валидации
  membership, lock или invitation документа приводит к отказу без записи
  (никогда не повышает права и не создаёт частичное состояние).
- `requireNotInMaintenanceMode` — первая операция внутри транзакции (через
  `txn.get()`), что закрывает TOCTOU-окно тем же механизмом, что и в
  `createCompany` (retry всей транзакции при изменении read-set).
- Raw token: генерируется один раз до транзакции; не имеет пути ни в один
  Firestore-документ (у `buildPendingInvitationDocument` физически нет
  параметра для него); не логируется; возвращается ровно один раз в ответе.
- Response — `.strict()`-схема, структурно не может содержать `tokenHash`.
- Повреждённые/несовпадающие lock/invitation документы никогда не
  раскрываются клиенту — единый generic `internal_error`, без содержимого
  документа, ID или указания, какой именно инвариант нарушен.
- `writeAuditEvent` вызван с той же транзакцией — audit event либо
  коммитится вместе с invitation+lock, либо не коммитится вовсе; в audit
  не попадают email/role/token/tokenHash.
- Ни один путь кода не создаёт Firebase Auth пользователя и не
  инициирует отправку письма (проверено тестом #18 и отсутствием таких
  вызовов в diff).

`SEC_006_STAGE2B_CHANGES_REQUIRED` (round 1) признал основную архитектуру
`listInvitations` (авторизацию, защиту данных, изоляцию компаний)
правильной, но указал 3 исправимых несоответствия.

1. **Cursor не полностью валидировался: `createdAtSeconds` без диапазона,
   `inviteId` допускал `/`.** Исправлено в
   `functions/src/schemas/invitation.ts`:
   - `createdAtSeconds` теперь ограничен документированным диапазоном
     Firestore `Timestamp` — `-62_135_596_800..253_402_300_799`
     (0001-01-01T00:00:00Z .. 9999-12-31T23:59:59.999999999Z).
   - `inviteId` в схеме курсора теперь использует новый
     `cursorDocumentIdString` (`nonEmptyString.max(200).regex(/^[^/]+$/)`)
     вместо общего `idLikeString` — не допускает `/`, так как это значение
     используется напрямую как `FieldPath.documentId()`.
   - Дополнительно, как defense-in-depth: новая функция
     `timestampFromCursorPayload()` в `functions/src/lib/invitationListing.ts`
     оборачивает конструктор `new Timestamp(...)` в `try/catch` →
     `AppError('invalid_request')` — даже если диапазонная проверка схемы
     когда-либо будет ослаблена или границы Firestore изменятся, конструктор
     не сможет выбросить необработанное исключение, попадающее в
     `internal_error`. `functions/src/index.ts` теперь вызывает эту функцию
     вместо прямого `new Timestamp(...)`.
   - Добавлены unit-тесты: диапазон (`InvitationsCursorPayloadSchema`
     напрямую и через `decodeInvitationsCursor`) — отказ чуть за
     пределами min/max, точное принятие НА границах, отказ для
     `Number.MAX_SAFE_INTEGER`; slash в `inviteId` — отказ; отдельный
     unit-тест `timestampFromCursorPayload` на defense-in-depth (подающий
     значение, которое обошло бы схему). Добавлены emulator-тесты через
     реальный callable: cursor с `createdAtSeconds` вне диапазона →
     `invalid_request` (не `internal_error`); cursor с `/` в `inviteId` →
     `invalid_request`.
2. **Lookahead-документ (`pageSize + 1`) не проверялся.** Исправлено в
   `functions/src/index.ts`: теперь ВСЕ документы из `snap.docs` (включая
   тот самый lookahead-документ) проходят `InvitationDocumentSchema` ДО
   какой-либо нарезки на страницу — `slice(0, pageSize)` применяется
   только к уже полностью провалидированному массиву. Повреждённый
   документ в любой позиции результата запроса (включая последнюю,
   «лишнюю» позицию) теперь гарантированно приводит к `internal_error` для
   всего вызова, а не к успешному ответу с `nextCursor`. Добавлен
   emulator-тест: `pageSize` валидных документов + один повреждённый
   документ, специально сконструированный так, чтобы попасть ИМЕННО в
   `(pageSize+1)`-ю позицию (самый старый по `createdAt`) → немедленный
   `internal_error`.
3. **Проверка read-only не охватывала `invitationLocks`.** Исправлено в
   `functions/test/emulator/listInvitations.test.ts`: тест «до/после»
   теперь дополнительно сидирует lock через `seedInvitationLockDoc` перед
   вызовом и подтверждает его побайтовую неизменность (`getInvitationLockDoc`
   до и после) наравне с invitations/memberships/audit events.

## Security review

- Авторизация полностью fail-closed: `companyId` — только ключ поиска;
  единственный источник решения — `requireActiveMember` +
  `requireRole(['admin'])` для ИМЕННО того `companyId`, что передан в
  запросе. Admin компании A, передавший `companyId: B`, получает
  `membership_not_found` до какого-либо чтения invitations (доказано
  тестом #7).
- Курсор — не источник авторизации: даже валидно закодированный курсор с
  ЧУЖИМ `companyId` отклоняется явной проверкой
  `cursorPayload.companyId !== input.companyId` до выполнения запроса.
- Ответ строится ТОЛЬКО через `mapInvitationDocumentToListItem` — этой
  функции физически негде взять `tokenHash`/`companyId`/`lockId` для
  ответа: они просто не входят в её allowlist. `.strict()` на
  `InvitationListItemSchema` делает это дополнительно проверяемым.
- Повреждённый invitation-документ (не проходящий `InvitationDocumentSchema`)
  всегда приводит к отказу ВСЕГО вызова (`internal_error`), не к частичному
  списку — предотвращает как утечку сырого содержимого, так и
  неочевидное «тихое» игнорирование повреждённых записей.
- Курсор проходит три независимых уровня валидации перед использованием:
  base64url-формат → JSON-парсинг → строгая Zod-схема (версия/типы/
  диапазон/неизвестные поля) — любой сбой на любом уровне даёт ОДИН и тот
  же безопасный `invalid_request`, никогда не раскрывая, на каком именно
  уровне и почему разбор не удался.
- listInvitations не пишет ничего: ни в `invitations`, ни в
  `invitationLocks`, ни в `audit_events`, ни в Auth — подтверждено
  побайтовым сравнением снимков до/после (тест #16) и явной проверкой
  отсутствия Auth-пользователя (тест #17).

## Известные ограничения

- **Пре-существующий timing-flake в `root: npm run test:migration`**,
  никак не связанный с этой задачей (SEC-006 Stage 2b не трогает `scripts/`
  вообще): один прогон дал `transactionalEnable racer A` failure
  (гоночный тест из более раннего SEC-00x, использующий тот же паттерн
  «выстрелить несколько конкурентных операций и проверить итог», что и
  ранее уже наблюдавшаяся хрупкость в `createCompany.test.ts`'s
  maintenance-mode race). Немедленный повторный прогон — 570/570 чисто.
  Зафиксировано честно, не скрыто; не исправлялось (чужой TASK_ID, не
  входит в Stage 2b).
- Firestore Emulator не требует реально развёрнутого composite index для
  выполнения такого запроса (в отличие от production) — добавленный
  `firestore.indexes.json` не был и не мог быть протестирован «а действительно
  ли production потребовал бы именно этот индекс», поскольку это
  проверяется только реальным Firestore при деплое/выполнении, что явно
  запрещено этой задачей. Состав индекса выведен из документированных
  правил Firestore (equality + multi-field orderBy требует composite
  index) и из структуры самого запроса — уверенность высокая, но не
  экспериментально подтверждена в этом PR.
- `Object.keys(item)`-стиль строгих ассертов в тестах явно перечисляет
  ожидаемые поля — при будущем добавлении нового публичного поля в
  `InvitationListItemSchema` эти тесты потребуют обновления (ожидаемо и
  предпочтительно: они должны падать, а не молча пропускать новое поле).
