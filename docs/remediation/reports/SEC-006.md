## Почему изменения входят в текущий пункт

Все перечисленные файлы реализуют исключительно
`inviteMember({ companyId, email, role })` и его прямые зависимости
(генерация/хеширование токена, response-схема, один новый код ошибки,
тестовая инфраструктура для этого callable). `vitest.config.mts` — не
логика продукта, а исправление тестовой инфраструктуры, ставшее
необходимым строго из-за добавления второго emulator-тестового файла в
рамках этой же задачи (без него нельзя было бы честно подтвердить «полный
emulator suite дважды зелёный», что требуется чек-листом). Ничего из
`listInvitations`/`cancelInvite`/`resendInvite`/`previewInvite`/
`acceptInvite`, UI, отправки писем, создания Auth-пользователя, Rules для
`members`, деплоя — не реализовано и не тронуто (согласно явному
ограничению scope).

## Round 2: исправления по независимому аудиту

`SEC_006_STAGE2_CHANGES_REQUIRED` (round 1) признал сам callable корректным
(авторизация, транзакционный lock, токен вне retry-цикла, SHA-256, атомарные
invitation/lock/audit, fail-closed на повреждённых данных), но указал 5
пробелов в доказательной части. Исправляющий коммит: см. `git log` этой
ветки после коммита `17d2570` (SEC-006 Stage 2: add inviteMember server
callable).

1. **`expiresAtUtc` — только непустая строка, а не строгий UTC ISO.**
   Исправлено: `InviteMemberResponseSchema.expiresAtUtc` теперь
   `z.iso.datetime()` (Zod v4) — принимает ровно формат
   `Date.prototype.toISOString()` (миллисекунды, суффикс `Z`), отклоняет
   любой другой offset/формат. Добавлены unit-тесты (принимает реальный
   `toISOString()`; отклоняет `+02:00`, дату без времени, произвольную
   строку). В emulator happy-path добавлен точный assert:
   `Date.parse(response.expiresAtUtc) === (stored.expiresAt as Timestamp).toMillis()`.
2. **Happy-path не читал audit event.** Исправлено: добавлен хелпер
   `getAuditEvents(companyId)` в `functions/test/emulator/helpers.ts`;
   happy-path тест теперь читает реальный audit-документ и проверяет точный
   набор полей (`{action, actorUid, createdAt, targetUid}`), `action ===
   'member_invited'`, `targetUid === null`, и явное отсутствие
   `token`/`tokenHash`/`email`/`role` — включая сериализованную проверку,
   что email нигде в audit-событии не встречается.
3. **Негативные тесты считали только invitations.** Исправлено: добавлен
   общий хелпер `expectNoWritesAtAllFor(companyId, email)` (0 invitations, 0
   lock, 0 audit events), применён к unauthenticated, unverified, non-admin
   (viewer+accountant), cross-company, malformed-payload и maintenance
   тестам. К трём corrupted-state тестам (сценарий 16) также добавлен
   явный `countAuditEvents(...) === 0`.
4. **«Forced retry» тест не доказывал факт retry.** Исправлено правильным
   способом, а не патчем существующего теста: `inviteMember`
   рефакторен — транзакционное тело вынесено в отдельный, независимо
   unit-тестируемый модуль `functions/src/lib/inviteMemberTransaction.ts`
   (`runInviteMemberTransaction`), который НЕ импортирует
   `generateRawInvitationToken`/`hashInvitationToken`/`node:crypto` вообще —
   структурно не может их вызвать. `performInviteMember` (новый
   экспорт в `functions/src/index.ts`) принимает инъецируемый
   `runTransactionImpl` (по умолчанию — реальный `db.runTransaction`).
   Новый `functions/test/unit/inviteMemberTransaction.test.ts`:
   - структурная проверка (`import`-строки модуля не содержат имён
     генератора/хешера/`node:crypto`);
   - поведенческая проверка — инъецированный `runTransactionImpl`,
     который явно вызывает update-функцию ДВАЖДЫ против двух фейковых
     `Transaction` (без Emulator), и assert:
     `generateRawInvitationToken`/`hashInvitationToken` вызваны РОВНО ОДИН

     `tokenHash`;

     попытке (гонка с параллельным победителем) — токен всё равно
     сгенерирован один раз.
   Старый emulator-тест (сценарий 17) сохранён как дополнительная
   эмпирическая проверка, его комментарий переписан честно: он не
   доказывает факт retry сам по себе, авторитетное доказательство — новый

## Security review

- Авторизация полностью fail-closed: любая ошибка чтения/валидации
  membership, lock или invitation документа приводит к отказу без записи
  (никогда не повышает права и не создаёт частичное состояние).
- `requireNotInMaintenanceMode` — первая операция внутри транзакции (через
  `txn.get()`), что закрывает TOCTOU-окно тем же механизмом, что и в
  `createCompany` (retry всей транзакции при изменении read-set).
- Raw token: генерируется один раз до транзакции; не имеет пути ни в один
  Firestore-документ (у `buildPendingInvitationDocument` физически нет
  параметра для него); не логируется; возвращается ровно один раз в ответе.
- Response — `.strict()`-схема, структурно не может содержать `tokenHash`.
- Повреждённые/несовпадающие lock/invitation документы никогда не
  раскрываются клиенту — единый generic `internal_error`, без содержимого
  документа, ID или указания, какой именно инвариант нарушен.
- `writeAuditEvent` вызван с той же транзакцией — audit event либо
  коммитится вместе с invitation+lock, либо не коммитится вовсе; в audit
  не попадают email/role/token/tokenHash.
- Ни один путь кода не создаёт Firebase Auth пользователя и не
  инициирует отправку письма (проверено тестом #18 и отсутствием таких
  вызовов в diff).

## Round 2: исправления по независимому аудиту

`SEC_006_STAGE2B_CHANGES_REQUIRED` (round 1) признал основную архитектуру
`listInvitations` (авторизацию, защиту данных, изоляцию компаний)
правильной, но указал 3 исправимых несоответствия.

1. **Cursor не полностью валидировался: `createdAtSeconds` без диапазона,
   `inviteId` допускал `/`.** Исправлено в
   `functions/src/schemas/invitation.ts`:
   - `createdAtSeconds` теперь ограничен документированным диапазоном
     Firestore `Timestamp` — `-62_135_596_800..253_402_300_799`
     (0001-01-01T00:00:00Z .. 9999-12-31T23:59:59.999999999Z).
   - `inviteId` в схеме курсора теперь использует новый
     `cursorDocumentIdString` (`nonEmptyString.max(200).regex(/^[^/]+$/)`)
     вместо общего `idLikeString` — не допускает `/`, так как это значение
     используется напрямую как `FieldPath.documentId()`.
   - Дополнительно, как defense-in-depth: новая функция
     `timestampFromCursorPayload()` в `functions/src/lib/invitationListing.ts`
     оборачивает конструктор `new Timestamp(...)` в `try/catch` →
     `AppError('invalid_request')` — даже если диапазонная проверка схемы
     когда-либо будет ослаблена или границы Firestore изменятся, конструктор
     не сможет выбросить необработанное исключение, попадающее в
     `internal_error`. `functions/src/index.ts` теперь вызывает эту функцию
     вместо прямого `new Timestamp(...)`.
   - Добавлены unit-тесты: диапазон (`InvitationsCursorPayloadSchema`
     напрямую и через `decodeInvitationsCursor`) — отказ чуть за
     пределами min/max, точное принятие НА границах, отказ для
     `Number.MAX_SAFE_INTEGER`; slash в `inviteId` — отказ; отдельный
     unit-тест `timestampFromCursorPayload` на defense-in-depth (подающий
     значение, которое обошло бы схему). Добавлены emulator-тесты через
     реальный callable: cursor с `createdAtSeconds` вне диапазона →
     `invalid_request` (не `internal_error`); cursor с `/` в `inviteId` →
     `invalid_request`.
2. **Lookahead-документ (`pageSize + 1`) не проверялся.** Исправлено в
   `functions/src/index.ts`: теперь ВСЕ документы из `snap.docs` (включая
   тот самый lookahead-документ) проходят `InvitationDocumentSchema` ДО
   какой-либо нарезки на страницу — `slice(0, pageSize)` применяется
   только к уже полностью провалидированному массиву. Повреждённый
   документ в любой позиции результата запроса (включая последнюю,
   «лишнюю» позицию) теперь гарантированно приводит к `internal_error` для
   всего вызова, а не к успешному ответу с `nextCursor`. Добавлен
   emulator-тест: `pageSize` валидных документов + один повреждённый
   документ, специально сконструированный так, чтобы попасть ИМЕННО в
   `(pageSize+1)`-ю позицию (самый старый по `createdAt`) → немедленный
   `internal_error`.
3. **Проверка read-only не охватывала `invitationLocks`.** Исправлено в
   `functions/test/emulator/listInvitations.test.ts`: тест «до/после»
   теперь дополнительно сидирует lock через `seedInvitationLockDoc` перед
   вызовом и подтверждает его побайтовую неизменность (`getInvitationLockDoc`
   до и после) наравне с invitations/memberships/audit events.

## Round 3: исправления по повторному независимому аудиту

`SEC_006_STAGE2B_CHANGES_REQUIRED_ROUND_2` подтвердил, что все 3 находки
round 1 исправлены корректно, и указал 2 новых точечных замечания.

1. **Проверка `inviteId` всё ещё неполная — не покрывала `.`/`..`/
   `__reserved__`.** Firestore официально запрещает document ID, равный
   `.` или `..`, и document ID, соответствующий `/^__.*__$/`
   (https://firebase.google.com/docs/firestore/quotas) — до этого исправления
   такие значения проходили `cursorDocumentIdString` (которая исключала
   только `/`) и могли бы завершиться ошибкой уже внутри самого Firestore,
   что превратилось бы в `internal_error` вместо стабильного
   `invalid_request`. Исправлено в `functions/src/schemas/invitation.ts`:
   `cursorDocumentIdString` теперь дополнена `.refine(...)`, отклоняющим
   `value === '.'`, `value === '..'` и `/^__.*__$/.test(value)`, точно как
   было указано в замечании. Добавлены:
   - unit-тесты на уровне схемы (`InvitationsCursorPayloadSchema` напрямую)
     для `.`/`..`/`__reserved__`/`__x__`, плюс sanity-тест, что значения,
     лишь СОДЕРЖАЩИЕ точки/подчёркивания без совпадения с запрещёнными
     формами (`invite.with.dots`, `_single_underscore_`), по-прежнему
     принимаются;
   - unit-тесты через `decodeInvitationsCursor` (тот же реальный путь
     декодирования, что использует callable) для `.`/`..`/`__reserved__`;
   - emulator-тесты через реальный callable (`it.each(['.', '..',
     '__reserved__'])`) — все три дают `invalid_request`.
2. **Не была выполнена emulator-проверка ровно граничных значений
   диапазона.** До этого исправления emulator-тест через реальный
   callable проверял только `Number.MAX_SAFE_INTEGER` (заведомо и грубо
   вне диапазона) — не сами точные граничные значения `-62135596801` и
   `253402300800` (ровно на 1 секунду за пределами документированного
   диапазона Firestore `Timestamp`), которые были явно и буквально
   запрошены предыдущим аудитом. Добавлен `it.each` emulator-тест через
   реальный callable, подтверждающий `invalid_request` для обоих точных
   значений.

## Security review

- Авторизация полностью fail-closed: `companyId` — только ключ поиска;
  единственный источник решения — `requireActiveMember` +
  `requireRole(['admin'])` для ИМЕННО того `companyId`, что передан в
  запросе. Admin компании A, передавший `companyId: B`, получает
  `membership_not_found` до какого-либо чтения invitations (доказано
  тестом #7).
- Курсор — не источник авторизации: даже валидно закодированный курсор с
  ЧУЖИМ `companyId` отклоняется явной проверкой
  `cursorPayload.companyId !== input.companyId` до выполнения запроса.
- Ответ строится ТОЛЬКО через `mapInvitationDocumentToListItem` — этой
  функции физически негде взять `tokenHash`/`companyId`/`lockId` для
  ответа: они просто не входят в её allowlist. `.strict()` на
  `InvitationListItemSchema` делает это дополнительно проверяемым.
- Повреждённый invitation-документ (не проходящий `InvitationDocumentSchema`)
  всегда приводит к отказу ВСЕГО вызова (`internal_error`), не к частичному
  списку — предотвращает как утечку сырого содержимого, так и
  неочевидное «тихое» игнорирование повреждённых записей.
- Курсор проходит три независимых уровня валидации перед использованием:
  base64url-формат → JSON-парсинг → строгая Zod-схема (версия/типы/
  диапазон/неизвестные поля) — любой сбой на любом уровне даёт ОДИН и тот
  же безопасный `invalid_request`, никогда не раскрывая, на каком именно
  уровне и почему разбор не удался.
- listInvitations не пишет ничего: ни в `invitations`, ни в
  `invitationLocks`, ни в `audit_events`, ни в Auth — подтверждено
  побайтовым сравнением снимков до/после (тест #16) и явной проверкой
  отсутствия Auth-пользователя (тест #17).

1. **Разделение «не найдено» vs «неверное состояние»**: отсутствующий
   invite ИЛИ invite чужой компании → `invitation_not_found` (одинаково,
   без oracle); существующий invite СВОЕЙ компании, но не `pending` →
   `invitation_not_pending`. Повреждённый (не проходящий
   `InvitationDocumentSchema`) документ — отдельно, `internal_error`
   (не создаёт oracle, так как недостижимо через обычный клиентский ввод —
   Rules полностью deny-all для этой коллекции).
2. **`invitationLocks` НЕ трогается.** Обоснование: `inviteMember`'s
   собственная логика уже трактует lock, указывающий на `revoked`
   (или `accepted`/expired-`pending`) invite, как безопасно заменяемый
   (см. `runInviteMemberTransaction`). Значит, отменённый invite,
   оставшийся «висеть» за старым lock, не блокирует следующее
   приглашение того же (companyId, email) — специальной очистки не
   требуется. Подтверждено emulator-тестом (lock побайтово не меняется).
3. **Response — `{ inviteId, revokedAtUtc }`.** Минимально, без
   email/role/companyId/tokenHash — по аналогии с
   `InviteMemberResponseSchema`.
4. **`revokedAt`/`updatedAt`** используют ОДНО и то же значение, вычисленное
   один раз через `new Date()` handler'а (не `FieldValue.serverTimestamp()`,
   которое нельзя синхронно прочитать для ответа) — тот же паттерн, что
   `expiresAt` в `performInviteMember`.
5. **Повторная отмена уже отменённого/принятого invite — не идемпотентна,
   а является ошибкой** (`invitation_not_pending`). Это осознанный выбор,
   консистентный с тем, как остальной код в этом пакете обрабатывает
   недопустимые переходы состояния (например, `assertNotLastAdmin`) —
   не «тихий успех», а явный сигнал вызывающему, что состояние уже
   изменилось.

## Round 2: исправления по независимому аудиту

`SEC_006_STAGE3_CHANGES_REQUIRED` (round 1) признал основную архитектуру
`cancelInvite` правильной, но указал 2 дефекта контракта и 2 пробела в
доказательствах.

1. **Oracle-защита была неполной.** В `cancelInviteTransaction.ts`
   документ полностью валидировался ДО проверки `companyId`, поэтому
   повреждённый ЧУЖОЙ invite давал `internal_error`, а отсутствующий —
   `invitation_not_found` — разные коды позволяли отличить класс
   существующих чужих документов. Исправлено: теперь сначала читается
   RAW (непровалидированное) поле `companyId` из документа; при
   несовпадении (или отсутствии/неверном типе) — сразу
   `invitation_not_found`, и только после подтверждения, что документ
   ЗАЯВЛЯЕТ принадлежность своей компании, выполняется полная
   `InvitationDocumentSchema`-валидация (её провал теперь — искренний
   `internal_error`, не создающий oracle, так как речь уже о документе
   СВОЕЙ компании). Добавлен emulator-тест: `Promise.allSettled` над
   повреждённым чужим invite и заведомо отсутствующим invite —
   оба дают one и тот же `invitation_not_found`, никогда `internal_error`.
2. **`companyId`/`inviteId` не проверялись как валидные Firestore document
   ID.** Экспортирована общая `FirestoreDocumentIdSchema` (обобщение уже
   существовавшей приватной `cursorDocumentIdString` из Stage 2b —
   отклоняет `/`, `.`, `..`, `/^__.*__$/`) и применена к обоим полям
   `CancelInviteRequestSchema` (было `idLikeString`). Добавлены unit-тесты
   для самой `FirestoreDocumentIdSchema` и для `CancelInviteRequestSchema`
   (оба поля, все 4 запрещённые формы + один allow-тест на «содержит
   точки/подчёркивания, но не совпадает с запрещённой формой»), и
   emulator-тесты через реальный callable (`it.each`) для обоих полей.
3. **Проверка «0 изменений» была неполной.** Добавлен общий хелпер
   `expectDenial()` (в `cancelInvite.test.ts`), который снимает snapshot
   `{invite, lock, memberships, auditCount}` до вызова и сверяет его
   побайтово после — применён теперь ко ВСЕМ denial-тестам (unauthenticated/
   unverified/insufficient_role/cross-company/maintenance/already-pending/
   forged-payload), вместо точечной проверки только `invite.status`.
4. **Полный пользовательский сценарий `inviteMember → cancelInvite →
   inviteMember` не был проверен.** Добавлен emulator-тест, вызывающий
   ВСЕ ТРИ операции через реальные callable (не через сидирование):
   старый invite остаётся `revoked`, новый — `pending` с новой ролью,
   lock атомарно указывает на новый inviteId, raw-токены обоих вызовов
   отсутствуют в сериализованном состоянии. **Явно зафиксированное
   расхождение**: ревью ожидало «audit-событий ровно два», но 3 реальных
   вызова callable (`inviteMember`, `cancelInvite`, `inviteMember`) по уже
   одобренному в Stage 2 паттерну (`writeAuditEvent` внутри той же
   транзакции, что и сама мутация) дают ровно 3 audit-события, не 2. Тест
   проверяет фактически корректное число (3) и содержит комментарий,
   explicitно указывающий на это расхождение — исправление теста под
   заявленное «2» потребовало бы либо пропустить реальную audit-запись
   (неверно), либо засеять первое приглашение напрямую в обход реального
   `inviteMember` (что обесценило бы саму цель теста «полный цикл через
   реальные callable»). Оставлено на усмотрение следующего раунда ревью.

## Ключевые архитектурные решения

1. **Lock-проверка сворачивает missing/corrupted/mismatched в один общий
   `internal_error`**, а не в отдельный код ошибки. Задание требовало «не
   чинить автоматически, отказать без записи», но не предписывало
   конкретный код. Решение принято по аналогии с тем, как остальной код
   пакета уже обрабатывает повреждённые/несовпадающие внутренние
   инварианты (`membership_data_error`, corrupted-invitation-document в
   Stage 2/3) — единый generic-код не создаёт oracle, различающий классы
   внутренней порчи данных, которые клиент в норме вообще не должен
   наблюдать (Rules — deny-all для `invitationLocks`).
2. **Cooldown-база — `lastSentAt ?? createdAt`, вычисляется от того же
   `nowTimestamp`, что попадает в запись.** Это гарантирует, что даже при
   внутреннем retry транзакции база и порог сравниваются с одним и тем же
   «сейчас», а не пересчитываются заново на каждой попытке.
3. **Токен/хеш/`expiresAt`/`now` — единый пакет `generated`, вычисленный
   один раз в `performResendInvite`.** `nowTimestamp` включён в этот же
   пакет (не вычисляется отдельно внутри транзакции) специально для того,
   чтобы cooldown-сравнение тоже было устойчиво к retry — расширение уже
   принятого в Stage 2/3 паттерна (там «now» использовался только для
   `expiresAt`/`revokedAt`, здесь дополнительно ещё и для порогового
   сравнения).
4. **`invitationLocks` не изменяется резендом** (по прямому требованию
   задания) — резенд продлевает/ротирует существующее приглашение под уже
   существующим lock, а не создаёт новое; лock уже корректно указывает на
   этот inviteId (иначе транзакция отказывает на шаге lock-проверки).
5. **(Round 1, независимый аудит) `lastSentAt` раньше `createdAt` —
   противоречивая хронология, а не просто «ещё один edge case».** Решение —
   тот же generic `internal_error` без auto-repair, что и у lock-проверки
   (пункт 1), а не новый специфичный код: это тоже случай «внутренний
   инвариант документа нарушен», о котором клиенту в норме нечего сообщать
   отдельно. `lastSentAt`, РОВНО равный `createdAt`, намеренно НЕ считается
   нарушением (легитимный edge case — создание и первый резенд в один и тот
   же момент).

## Security review

- Авторизация полностью fail-closed: `companyId`/`inviteId` — только
  lookup-ключи; решение принимает исключительно
  `requireActiveMember`+`requireRole(['admin'])` для ИМЕННО того
  `companyId`, что передан, плюс повторная проверка `invite.companyId ===
  input.companyId` внутри транзакции (унаследовано от Stage 3).
- Cross-company oracle закрыт тем же механизмом, что Stage 3: «не
  существует», «существует в другой компании» и «повреждён в другой
  компании» дают ОДИН и тот же `invitation_not_found`.
- **Новый для Stage 4 инвариант**: lock, не указывающий на именно этот
  inviteId (отсутствующий, повреждённый или указывающий на другой), не
  может быть auto-repaired и не приводит к записи — resend не способен
  «воскресить» приглашение, уже фактически замещённое `inviteMember`.
  Подтверждено отдельным сценарием, моделирующим точное состояние после
  реального `inviteMember`'s expired-replace, и гонкой с реальным
  `inviteMember`.
- Токен и его SHA-256 вычисляются один раз ДО транзакции; raw token не
  имеет пути ни в один Firestore-документ; не логируется; возвращается
  ровно один раз, только после успешного commit.
- Response — `.strict()`-схема (буквально тот же объект, что у
  `inviteMember`), структурно не может содержать tokenHash.
- `writeAuditEvent` вызван в той же транзакции — audit event либо
  коммитится вместе с обновлением invitation, либо не коммитится вовсе; в
  audit не попадают email/role/token/tokenHash.
- Время сервер-детерминировано (`nowTimestamp` вычислен обработчиком один
  раз, до транзакции, и переиспользуется и для cooldown-сравнения, и для
  записи `lastSentAt`/`updatedAt`) — подделанное клиентом время в payload
  отклоняется схемой (`.strict()` не допускает поле `lastSentAt`/`now` во
  входных данных вообще).
- Ни один путь кода не создаёт Firebase Auth пользователя.

## Известные ограничения

- Как и в предыдущих подпунктах, авторитетное доказательство «retry не
  пересчитывает token/tokenHash/expiresAt/now» — unit-тест с инъецированным
  transaction runner, а не emulator-тест (у Firestore Emulator нет
  публичного хука для форсирования внутреннего retry извне). Emulator-тест
  #29 — дополнительная эмпирическая проверка на реальном контеншне.
- Точная миллисекундная граница cooldown (`elapsed === COOLDOWN_MS` ровно)
  проверена только unit-тестом (`resendInviteTransaction.test.ts`), не
  emulator-тестом: реальная задержка Functions Emulator (round trip,
  проверки авторизации, чтения Firestore) делает margin меньше нескольких
  секунд ненадёжным на уровне emulator-теста — это наблюдалось на практике
  в этой же задаче (изначальный margin ±1ms/±500ms дал ложный failure,
  см. ниже) и задокументировано прямо в комментарии теста.
- **`acceptInvite` не существует** — принятие приглашения по новой,
  зарезенженной ссылке НЕ проверено сквозным emulator-тестом через
  `acceptInvite` (такого callable ещё нет). Проверено только то, что новый
  `tokenHash` персистится и заменяет старый; сквозная проверка «новый raw
  token действительно принимается» относится к будущему этапу, реализующему
  `acceptInvite`.
- **Пре-существующий timing-flake в `root: npm run test:migration`**, не

  первоначальной (до round 1) проверке один прогон дал `transactionalEnable
  racer A` failure (timeout 5000ms) в

     оказался флаки на реальном emulator: наблюдался ложный failure, когда
     «чуть меньше 60с» фикстура фактически превращалась в «чуть больше 60с»
     к моменту серверной проверки из-за реальной задержки round-trip.
     Исправлено расширением margin до `±5000ms` — точная граница
     по-прежнему доказывается unit-тестом без задержки.
  2. Тест гонки `resendInvite`-vs-`cancelInvite` изначально неверно
     предполагал взаимоисключающий исход («ровно один побеждает»), хотя эти
     две операции НЕ являются взаимоисключающими (единственное
     предусловие `cancelInvite` — `status === 'pending'`, которое
     `resendInvite` никогда не меняет) — исправлено на корректный инвариант
     (`cancelInvite` побеждает всегда; `resendInvite` либо тоже успевает,
     либо получает `invitation_not_pending` — оба исхода валидны и оба
     явно проверяются тестом), после явного анализа предусловий обеих
     операций. Никакая вероятность распределения между этими двумя
     исходами не заявляется и не измерялась — оба просто допустимы.
